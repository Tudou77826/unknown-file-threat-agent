# ATT&CK 评测案例讲解

> 对象：安全能力持续验证套件中的 31 个案例（29 个实验室重采案 + 2 个钉住基线案），逐案讲解、无一遗漏。
> 每个案例按三段讲解：这项技术在真实世界本来是什么；我们在靶机上如何构造它；
> AI 研判时依据了哪些证据（结论摘要引自 r12 全量评测的结案报告原文）。
> 阅读本文不需要了解套件的构建过程。

## 总览

套件以 ATT&CK 技术为坐标系，覆盖 19 种技术、20 个恶意案（含一条四阶段完整链）与 9 个良性镜像案，另含 2 个钉住基线案（c2 系列）。恶意与良性的行为形状刻意互为镜像——公钥驻留对配置管理公钥下发、脚本回连对厂商监控心跳——区分不靠行为外观，靠授权背景与证据链。

所有案例在独立 Linux 靶机上真实执行：编译与脚手架在审计窗口外完成（prepare 阶段），窗口内只发生攻击或运维动作本身；命令行与遥测中不出现靶场标识；外连端点使用绑定在回环设备上的保留地址 198.51.100.50 模拟外部主机。每个案例经三轮数据复核（答案泄露、靶场痕迹、证据缺口）与一次全量重采后进入评测。

评测结论（r12，每案两轮）：恶意案方向正确率 92%，结论距离 0.79；良性镜像案因当前环境缺少权威白名单工具存在系统性误报（已列入黄区对接后的整改项，本文不展开）。下文"AI 检出"一节引用的是模型自己的结案摘要。

## 恶意案例

### t1036-005 伪装驻留（T1036.005 Masquerading: Match Legitimate Name or Location）

**原景**：攻击者给恶意文件起合法软件的名字、或放进系统存放合法二进制的目录，利用运维对熟悉名字的注意力盲区和安全策略对系统路径的信任。真实世界常见形态：挖矿程序伪装成 `systemd-logind`/`kworker`、SSH 后门命名为 `sshd` 家族。防御方的识破点不在名字本身，而在组合证据：系统目录里的文件却不属于任何软件包、执行上下文不是 systemd 拉起、执行后出现外连。

**构造**：窗口内将一个后门 ELF 以 `sshd-helper` 之名安装到 `/usr/local/sbin` 并以 root 执行、回连 C2。反证数据同步提供：包归属查询返回"不属于任何已安装包"、部署台账在当前环境不可查询（结论为未知，不作为判定依据）。

**AI 检出**（两轮均 confirmed_malicious）：模型把投放链完整串起——"以 root 权限投递、伪装成 sshd 的 ELF 远控木马：落地后通过 install 安装到系统路径，随后立即以命令行参数携带外部地址与端口直接执行，并观察到对外的 TCP 出网连接"，并明确引用了"非包归属"与伪装命名的组合。

### t1070-006 时间戳回拨（T1070.006 Timestomp）

**原景**：攻击者篡改文件时间戳让恶意文件"看起来很老"，规避按新近度排序的排查流程。Linux 上典型手法是 `touch -r /bin/ls 恶意文件`。防御识破点：ext4 文件系统由内核维护的创建时间（birth）用户态改不了——修改时间早于创建时间在物理上不可能，除非有人篡改。

**构造**：窗口内投放载荷、执行回连后，以 `/bin/ls` 为参照回拨其 mtime。采集器在窗口结束后对声明的系统路径拍 stat 快照，`modify_time 2024-05-24` 早于 `birth_time 2026-10-12` 的矛盾作为可查询证据进入遥测。

**AI 检出**（confirmed_malicious / likely_malicious）：模型引用了三件套——"不属于任何软件包基线，由来源不明脚本复制、赋权并执行，执行后随即发起对固定外部端点的连接，并伴随以系统二进制为参照篡改文件时间戳的反取证行为"。

### t1027 混淆载荷（T1027 Obfuscated Files or Information）

**原景**：攻击者把恶意脚本编码（如 base64）后落盘，运行时解码直接管道进解释器执行——磁盘上永不出现明文，绕过基于文件内容扫描的检测。

**构造**：窗口内落盘 base64 编码的回连脚本 `beacon.enc`，`base64 -d | bash` 解码执行并回连。明文只存在于管道中。

**AI 检出**（两轮 likely_malicious）："确认存在一条以 beacon.enc 为载荷的编码执行链：解码该加密文件并通过 python 建立指向外部地址的反连（心跳含 beacon 字样），行为模式与后门/C2 回连高度吻合"。模型同时如实标注了保守的原因：初始入侵入口未能追溯。

### t1098-004 公钥驻留（T1098.004 SSH Authorized Keys）

**原景**：攻击者把自己的公钥追加进 root 的 authorized_keys，此后可用对应私钥随时正门登入，不依赖任何恶意进程。与合法的配置管理公钥下发在行为外观上完全一致，区分只在授权背景。

**构造**：窗口内生成攻击者密钥对（注释 maint-deploy），追加公钥到 `/root/.ssh/authorized_keys`，随即用该私钥尝试本机 SSH 登入（产生 USER_LOGIN 认证事件）。良镜像案 bb11 做完全相同的动作，但带配置管理部署记录。

**AI 检出**（likely_malicious / suspicious）：模型还原了完整链路——"生成隐藏路径下的 ed25519 攻击密钥、写入 authorized_keys、收紧权限，并立即用该私钥尝试登入"，并结合无部署凭证判向恶意。本案与镜像案的裁定依赖黄区权威白名单工具（见总览）。

### t1136-001 隐藏 root 账号（T1136.001 Local Account Creation）

**原景**：攻击者以 root 权限创建一个与 root 同 UID 的本地账号（`useradd -o -u 0`），此后可用普通登录方式以 root 等效权限进入系统——不依赖任何文件型后门。真实世界的挖矿蠕虫与 APT 横向移动后常用此招驻留。防御识破点：/etc/passwd 与 /etc/shadow 的变更可审计、UID 0 重复本身就是异常、新账号创建后随即产生登录会话（USER_ACCT 记录）几乎必是持久化。

**构造**：窗口内 `useradd -o -u 0 -M -N -s /bin/bash svcmaint` 写入账号文件，随即 `su` 切换产生真实会话。判定对象为 /etc/passwd；其写入事件带内容哈希与调查目标锚定一致，账号文件内容快照（含 svcmaint 的 UID 0 行）与 PAM 会话记录（USER_ACCT）均进入可查面。

**AI 检出**（两轮 likely_malicious）："由 run.sh 派生的 useradd 进程以 -o -u 0 参数创建了 UID 为 0 的账户 svcmaint，随后写入 /etc/passwd 与 /etc/shadow 并执行 su 验证，形成具有 root 等效权限的隐蔽账户，符合账户创建持久化（T1136）特征"——保守原因（"是否为合法运维脚本部署无法完全排除"）如实给出，授权背景的最终裁定同属黄区对接项。

### t1552-004 私钥窃取外传（T1552.004 Private Keys + T1567 Exfiltration）

**原景**：攻击者从失陷主机上收集已存在的 SSH 私钥（通常属于其他用户或备份账户），打包外传——这些钥匙往往能打开企业内其他机器。与"现场生成新密钥"是两种行为，前者才是窃取。

**构造**：窗口外预先存在属主为 ops 的登录密钥（属主、指纹、创建时间作为窗口前资产快照进入遥测）；窗口内复制该私钥到暂存目录、打包、POST 上传到外部接收端。接收端回执记录解析出的上传文件名、字节数与 SHA256，与发送端归档哈希一致——"收到的就是这个包"可验证。

**AI 检出**（两轮 suspicious，方向正确）：模型确认"真实的私钥窃取与外传事件：复制 ops 用户的 SSH 私钥到暂存目录（哈希与告警文件一致）、打包并以 curl 外传至外部地址，命令行证据完整"，保守原因同样如实给出——外传成功缺乏网络层印证、run.sh 来源不明。

### t1548-001 setuid 提权（T1548.001 Setuid and Setgid）

**原景**：攻击者以 root 放置一个设置 setuid 位的程序，此后任何低权限用户执行它都以 root 身份运行——经典的本地提权原语。防御识破点：chmod 4755 的属性变更可审计，且执行事件的 uid 与 euid 出现"非特权用户获得有效 root"的组合。

**构造**：窗口内 chown root:root + chmod 4755，随后以 nobody（uid 65534）执行并回连。进程事件的 uid/euid 双值是本案权威证据（此前版本只保留 euid，丢失"非特权用户"这半个事实）。

**AI 检出**（likely_malicious / 一轮方差 likely_benign）："由 root 执行 chown root:root 和 chmod 4755 设置为 SUID，随后以 nobody 身份（uid=65534）启动该文件时获得有效 uid 0（euid=0），并立即向外网地址发起连接"。第二轮的方差翻车是本套件已知的单轮波动，非证据缺陷。

### t1059-006 脚本回连（T1059.006 Python）

**原景**：用受害机上现成的解释器（Python/Perl）执行回连脚本，不引入新二进制依赖，是轻量后门和加载器的常见形态。与厂商监控 agent 的心跳在外观上同为"周期性外连"。

**构造**：窗口内落盘 Python 回连脚本，解释器执行，以秒级间隔向固定端点发起多次连接（网络事件的观测计数保留周期性证据）。

**AI 检出**（confirmed_malicious / likely_malicious）："判定为恶意后门/C2 样本：对固定外部地址发起高频回连，执行链、外联与文件落地均已由本机证据确认"，并给出处置建议"按主机失陷处置"。

### t1105 入口工具传输（T1105 Ingress Tool Transfer）

**原景**：攻击者初始立足后第一步往往是从自己控制的主机拉取工具（curl/wget 下载 ELF），把攻击装备搬进内网。良性运维从内部镜像下载工具与之外观相同，区分在下载源是否在批准清单。

**构造**：窗口外备好外部下载源；窗口内 curl 下载 ELF 到 `/tmp/.cache/ingress/`、chmod、执行回连。良镜像案 bb6 从批准镜像下载运维工具。

**AI 检出**（两轮 likely_malicious）："判定为大概率恶意的外部投递工具，符合 T1105 入口工具传输并疑似回连 C2：curl 从外部地址下载该 ELF，落地后立即 chmod 700 并执行，且执行后与同一外部地址的非标准端口通信"。

### t1037-004 rc.local 持久化（T1037.004 RC Scripts）

**原景**：`/etc/rc.d/rc.local` 是传统 SysV 启动脚本，某些发行版仍保留执行——攻击者向它追加一行即可在每次重启时以 root 拉起后门，比 systemd 更老旧也更少被监控。

**构造**：窗口内投放载荷、向 rc.local 追加启动项、执行回连。

**AI 检出**（confirmed_malicious / likely_malicious）："对 /etc/rc.d/rc.local 写入（rc-local 持久化，与告警 file_id 吻合），载荷执行后向外部地址回连"。

### t1053-003 cron 持久化（T1053.003 Cron）

**原景**：cron 是 Linux 最常用的持久化位置之一，`/etc/cron.d/` 下追加一个文件即实现周期执行。良性运维定时任务与之完全同形，区分在任务内容由谁、经什么流程部署。

**构造**：窗口内投放载荷、向 `/etc/cron.d/sysupd-maint` 写入每五分钟拉起载荷的任务、立即执行一次回连。良镜像案 bb4 注册运维清理 cron。

**AI 检出**（likely_malicious / confirmed_malicious）："数毫秒内连续完成落地、赋权、执行并外连固定 IP，同一秒内还创建 /etc/cron.d 持久化项，行为链完整且命名伪装（sysupd、.cache 隐藏目录）"。

### t1543-002 systemd 服务持久化（T1543.002 Systemd Service）

**原景**：现代 Linux 的标准持久化位置——写入 unit 文件并 enable，重启后由 init 系统以 root 拉起。监控套件的合法安装与之完全同形。

**构造**：窗口内投放载荷、写入 `sysupd.service` 单元、daemon-reload + enable、执行回连。良镜像案 bb8 安装整套监控（二进制+单元+cron）。

**AI 检出**（两轮 confirmed_malicious）："完整攻击链在本机证据内闭合：脚本串联完成文件落地、赋权、写入 systemd 服务单元（持久化）、启用服务并以 root 执行载荷，随后载荷立即外连固定远端地址的高位端口，形成持久化+C2 回连组合"。

### t1547-006 内核模块（T1547.006 Kernel Modules）

**原景**：内核态 rootlet 的起点——insmod 加载恶意 .ko 获得内核执行。现代发行版默认启用模块签名校验，未签名模块加载被拒；但"加载尝试"本身已是高价值信号。

**构造**：窗口外以 kbuild 编译最小内核模块；窗口内 insmod（在签名策略下预期失败，失败痕迹即证据）、枚举模块、清理。

**AI 检出**（likely_malicious / confirmed_malicious）："遥测确认 root 权限依次派生 kmod 尝试加载该模块、枚举模块列表并对名为 rootkit 的模块执行查询/卸载，同毫秒生成了 insmod 报错输出文件，提示加载尝试失败或报错"。

### t1574-006 LD_PRELOAD 劫持（T1574.006 Dynamic Linker Hijacking）

**原景**：把恶意 .so 放进 LD_PRELOAD，此后每个动态链接程序启动时都会先执行其中代码（构造函数回连是常见用法）——一次注入、全体进程受控。检测难点：环境变量与 .so 的只读打开都不直接进入审计日志。

**构造**：窗口外编译构造函数回连的共享库；窗口内以 LD_PRELOAD 劫持 /usr/bin/true 触发回连。本案权威证据是"无辜程序发起外连"+ 非包归属的 .so 文件。

**AI 检出**（两轮 insufficient_evidence）：模型正确识别了路径与命名特征"符合 LD_PRELOAD 劫持手法，具有可疑性"，但如实报告"文件创建、写入来源、加载执行与出网行为均无法证实"。这是套件当前的已知证据限制（下一轮采集将补 .so 的工作区副本锚定），不是模型能力缺陷。

### t1219 隧道/RAT 部署（T1219 Remote Access Software）

**原景**：投放反向隧道或 RAT 客户端并保持长连接出站——企业内网穿透的通用形态。特征是"投放-执行-长连接"三步在毫秒级完成。

**构造**：窗口内复制 ELF 到隐藏目录、赋权执行、维持 3 秒出站长连接供连接轮询捕获四元组。

**AI 检出**（两轮 likely_malicious）："呈现毫秒级一次性的投放-执行-回连链路，行为模式与反向隧道/RAT C2 回连高度一致。文件无哈希信誉"——模型还如实标注了信誉数据缺失。

### t1486 勒索加密（T1486 Data Encrypted for Impact）

**原景**：勒索软件对业务数据加密并改扩展名勒索。演练环境里的"加密"用对称 XOR 模拟（可恢复），行为链（遍历、加密、改名）保持真实。

**构造**：窗口外备好蜜罐业务数据（客户库凭据、发票文件）与备份；窗口内执行加密器、逐文件加密并改 `.locked` 后缀。

**AI 检出**（likely_malicious / confirmed_malicious）："对业务数据文件执行写入并重命名为 .locked，符合勒索软件加密+改名的典型行为链。未发现外联 C2 与持久化组件……定性为'很可能恶意'而非'确认恶意'"——保守理由与真实勒索通常伴生组件的常识一致。

### t1505-003 Web Shell（T1505.003 Server Software Component: Web Shell）

**原景**：向可被 Web 服务执行的目录写入一句话脚本，经 HTTP 请求参数执行任意命令——初始立足后的常驻控制通道。

**构造**：窗口外起好 HTTP 服务；窗口内向 `/var/www/html/` 写入 PHP web shell，并以 curl 携带命令参数触发一次。

**AI 检出**（suspicious / likely_malicious）："为无合法软件包归属的 PHP web shell，落地后被本机脚本以 curl 触发对外部端点的回连请求，特征与 C2/命令执行通道一致"。

### t1005+t1560-001 凭据收集归档（T1005 Data from Local System + T1560.001 Archive Collected Data）

**原景**：外传前的准备动作——从本机收集凭据材料（shadow 提取物、云密钥），打包暂存等待外传。单独看每一步都可能是运维动作，链条组合才暴露意图。

**构造**：窗口内在暂存目录创建凭据文件并打包为 staging.tar.gz（判定对象即该归档）。

**AI 检出**（两轮 likely_malicious）："毫秒级窗口内创建凭据文件（云凭据与 shadow 提取物）并打包，构成典型的凭据收集→暂存→归档链（对应 T1003.008、T1074.001、T1560.001）"。

### t1567-002 外传上传（T1567.002 Exfiltration to Cloud Storage）

**原景**：把收集的数据经 HTTP 上传到攻击者控制的外部端点（对象存储、 Pastebin 形态）。检测关键是"上传动作+接收成功"的对应，而非仅一次 POST 请求。

**构造**：窗口内复制敏感文件、打包、POST 上传；接收端回执（含解析出的文件 SHA256）与发送端归档哈希一致，上传回执文件内容进入可查面。

**AI 检出**（likely_malicious / suspicious）："确认存在一条完整的本机数据外传链条：复制 /etc/passwd、打包、以 curl 向外部地址发起上传，同时生成上传回执文件"。

### chain-001 完整入侵链（T1105 + T1053.003 + T1098.004 + T1567.002）

**原景**：真实入侵不是单点技术而是链条：下载投放 → 执行回连 → 持久化（cron + 公钥双保险）→ 敏感数据收集外传。防御方的难点是跨阶段归因——证明后续动作由同一载荷派生，而非同机上无关的巧合事件。

**构造**：窗口外备好下载源与双角色接收端；窗口内 curl 下载 stage1.elf、执行回连后，**由载荷自身 fork/exec 派生子进程**执行二阶段脚本——写入 cron 驻留、追加公钥并尝试登入、打包外传。进程树父子关系使跨阶段归因可验证；cron 内容、authorized_keys 追加行、上传回执的内容均作为物证进入可查面。

**AI 检出**（两轮 confirmed_malicious）："`/tmp/.sysupd/stage1.elf` 由外部地址下载、chmod 后以 root 执行并向外部 C2 回连，随后完成 SSH 密钥持久化、cron 持久化及本地数据收集打包，构成完整的入侵后门链"。

## 良性镜像案例

### bb2 变更单备份

**原景**：最普通的日常运维——按变更单备份应用数据。它存在的意义是校准误报底线：纯文件打包操作不应触发告警。

**构造**：窗口内将 `/opt/appdata` 打包归档到 `/var/backups/admin/`，无网络、无持久化。

**AI 检出**（insufficient / likely_benign）：第一轮调查覆盖不足，模型如实报告证据不足而非猜测；第二轮倾向良性。

### bb3 运维工具部署

**原景**：部署一个健康检查脚本并执行一次——无外连、无持久化的最小运维动作。

**构造**：窗口内将健康检查工具部署到 `/usr/local/bin/ops-healthcheck` 并执行（输出健康状态文件）。

**AI 检出**（两轮 likely_benign）："行为链（创建→chmod 700→执行）符合运维工具部署模式，未观察到网络外连、持久化或后续可疑进程，倾向判定为良性运维脚本；因缺少脚本内容与信誉数据，无法完全排除伪装风险"——判定正确且保守理由如实。

### bb4 运维 cron（镜像 t1053-003）

**构造**：注册每日日志清理 cron 并执行一次，操作范围限定策略在案。
**AI 检出**：两轮 suspicious——与恶意镜像同形，模型无法从行为区分（裁定依赖权威白名单工具）。

### bb5 编译产物心跳（镜像 t1059-006）

**构造**：部署编译的二进制并向批准端点注册心跳。
**AI 检出**：likely_malicious / suspicious——同上，镜像误报的典型。

### bb6 镜像下载（镜像 t1105）

**构造**：从批准镜像下载运维工具、安装、执行；下载失败必须显式失败。
**AI 检出**：两轮 likely_malicious——同上。

### bb7 厂商监控 agent（镜像 t1059-006）

**构造**：安装厂商 agent，按清单声明的间隔（2 秒 × 3 次）心跳回连批准端点，部署清单内容（产品名、端点、间隔、安装人）进入可查面。
**AI 检出**：suspicious / likely_malicious——模型查到了端点批准记录但以"批准记录缺乏批准人与原因"不予采信。这正是当前自建基线缺乏权威性的体现（黄区对接整改项）。

### bb8 运维套件安装（镜像 t1543-002 + t1053-003）

**构造**：一次装齐二进制 + systemd 单元 + cron 报告的监控套件；套件清单带每个组件的路径与真实哈希。
**AI 检出**：两轮 likely_malicious——与 bb7 同因。

### bb9 日志轮转（镜像 T1070/T1485 类清除行为）

**构造**：按在案策略轮转日志（gzip 归档到备份目录、删除原件、归档保留），策略文件内容可查，轮转脚本部署在 `/usr/local/bin`。
**AI 检出**（benign / likely_benign）：**全案最干净的良性判定**——"全部可见行为与标准应用日志轮转一致：仅对 /var/log/applog 下的日志执行归档与删除，全程无网络活动、无服务或持久化定义，未见日志清除、数据暂存或外传特征"。说明当反证（策略+范围）可见时模型能正确放行。

### bb11 配置管理公钥下发（镜像 t1098-004）

**构造**：配置管理预生成运维密钥（注释 ops-deploy@cfgmgmt），按部署记录（工单号 OPS-2026-1013）下发公钥到 root 并做一次本机登入验证；ansible 任务定义与部署记录内容可查。
**AI 检出**（两轮 likely_benign）："写入进程链清晰、上下文高度符合运维配置管理行为：唯一外连为目标本机 22 端口，无任何外部地址"——与镜像 t1098 的判定形成正确对照，说明当部署凭证可见时模型能区分同形行为。

## 钉住基线案（c2 系列）

这两案来自数据完整度坐标系（合成参考数据集，确定性种子生成），与上述 29 案的靶场采集管线不同源；它们作为固定基线钉在正式套件中，c2-malicious-elf 也是所有单案冒烟验证的标准用例。

### c2-malicious-elf 后门基线（T1071.001 + T1543.002）

**原景**：教科书式 Linux 后门组合：ELF 投放到隐藏路径，systemd 服务持久化，以固定间隔向 C2 的 443 端口直连回传——应用层协议伪装成正常 HTTPS 流量形态。

**构造**：合成遥测覆盖进程树（sshd→bash 拉起）、文件落地、服务定义/启用/启动、周期外连与心跳收发；与靶场案不同，本案的 C2 端点（203.0.113.50:443）在端点基线中明确标记为**未批准**——反证直接可用。

**AI 检出**（confirmed / likely_malicious）："无签名 ELF 以 root 执行，由 sshd→bash 进程树拉起，随后创建并 enable/start 自定义 systemd 服务实现持久化，并以固定 60 秒间隔向基线标记为未批准的外部地址发起周期性外连，伴随低流量收发，符合 C2 通信特征"——注意模型明确引用了"未批准端点"反证，与靶场案中自建基线不被采信形成对照：当反证数据可信时，模型会用它。

### c2-benign-baseline 良性基线

**原景**：合法厂商监控代理的标准形态：包管理器安装、systemd 托管、周期心跳回连厂商采集端点。用于误报率统计的基准锚点。

**构造**：合成遥测中该代理由已签名的合法软件包拥有、服务单元正规、父进程为 systemd（pid 1）、仅周期性出站 443 心跳——每项反证都齐备且自洽。

**AI 检出**（insufficient / benign）：第一轮调查覆盖不足，模型选择如实报告证据不足而非猜测；第二轮完整引用反证链判良性——"由已签名且合法的软件包拥有，通过正规 systemd 服务单元定义，进程由 systemd 直接派生，网络行为仅限周期性心跳，无异常文件写入"。与 bb7 的对照说明问题不在模型而在数据权威性：包归属为"已签名合法包"时（本案），模型采信；自建 CMDB 批准记录（bb7）则不被采信。
