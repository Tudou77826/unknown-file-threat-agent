## 0. 本次 Session 最新结论

### 0.1 项目最终定位

本项目不是重新实现一套 CDE 或未知文件恶意检测算法，而是：

> 以 CDE 和现有检测链路发现的 Linux 未知文件为调查锚点，消费已有表记录和上下文；由大模型根据每一步证据自主提出问题、选择下一步数据并动态扩大调查范围，完成跨文件、跨时间、跨主机的深度关联，最终还原该未知文件执行前、执行中、执行后的行为路径和可能的攻击路径，判断它是否参与未知后门、数据窃取或未知勒索等真实攻击，并输出可解释、可追溯、可举证的研判结论。

最简表述：

```text
CDE 发现未知文件；
Agent 围绕未知文件还原攻击路径。
```

“Agent 调查异常点之间的关系”只是实现手段，不是项目最终目标。最终目标始终是还原一个未知文件相关的行为/攻击路径。

### 0.2 CDE、现有产品链路和 Agent 的边界

```text
CDE 引擎：
以静态文件检测为核心
→ 文件特征分析
→ 黑/白/灰/未知分类
→ 不持续采集完整运行时行为

现有产品链路：
保存 CDE 检测结果
→ 附带当前已有的文件、触发进程、回溯进程链、用户、资产、
   容器、部分网络字段和异常事件
→ 形成三张表或等价 JSON

威胁智能研判 Agent：
优先使用已有表数据
→ 识别这些数据无法回答的问题
→ 按需获取补充的终端、网络和静态分析证据
→ 跨文件、跨时间、跨主机推理
→ 还原路径并形成案件级结论
```

Agent 不重复完成：

- 文件发现。
- CDE 静态检测。
- 黑白灰和未知分类。
- 现有规则已经产生的单点检测告警。

Agent 重点完成规则匹配难以处理的：

- 不确定案件中的开放式调查。
- 根据中间结果改变下一步。
- 多个文件之间的因果关联。
- 告警前后及长期潜伏的时间关联。
- 多台主机之间的传播和影响关联。
- 攻击解释与合法解释的比较。
- 反证、缺失证据和不确定性表达。

### 0.3 为什么需要从规则匹配转向智能推理

项目背景是应对 AI 原生攻击和海量告警。仅依赖规则匹配存在：

- 新变种未命中已有规则。
- 单点告警无法表达完整攻击链。
- 同一攻击被拆成大量孤立告警。
- 告警之间缺少跨时间和跨主机关联。
- 合法运维与攻击行为表面相似，误报较高。
- 潜伏、低频 C2、分阶段窃取等隐蔽行为难以发现。

大模型 Agent 的价值不是用自然语言重新写一套规则，而是：

```text
读取当前案情
→ 形成候选假设
→ 找到最关键的未知问题
→ 自主选择下一类证据
→ 分析结果并更新假设
→ 决定是否跨文件、扩展时间或跨主机
→ 直到形成可举证结论或确认数据不足
```

确定性程序仍负责日志解析、时间转换、Hash 比较、实体关联、Schema 校验和安全控制；这些属于可靠的数据处理，不是以固定规则替代案件推理。

### 0.4 三类核心场景

#### 未知劫持后门/远控

重点关注：

- 隐藏或伪装进程、删除后运行。
- 关键进程劫持、异常动态库、`LD_PRELOAD`、内核模块等。
- cron、systemd、SSH key、账号、sudoers、启动配置等持久化。
- 反向连接、监听、周期回连、DNS 隧道、WebShell、代理和转发。
- 使用相同账号、密钥、文件或 C2 扩展到其他主机。

#### 未知数据窃取/木马

重点关注：

- 主机、目录、数据库和敏感资产枚举。
- 敏感文件、SSH 私钥、Token、证书、浏览器会话和云凭据访问。
- 数据库导出、文件归集、压缩、加密和临时暂存。
- HTTPS、SCP/SFTP、DNS、代理、云存储等外传。
- 使用窃取凭据访问其他主机或容器。

#### 未知勒索

重点关注：

- 大量或高频文件读取、改写、重命名、删除和加密。
- 数据库、备份、安全和业务关键服务停止。
- LVM、Btrfs、ZFS、云盘、虚拟化或备份系统快照破坏。
- 备份任务、恢复配置、挂载和共享存储破坏。
- 勒索信、登录提示或 Web 页面篡改。
- 多主机、容器和共享存储上的同步影响。

三个场景可能串联：

```text
后门潜伏和远控
→ 凭据访问与跨主机扩展
→ 数据发现、归集和外传
→ 停止服务与破坏备份
→ 批量加密和勒索
```

三个场景是业务调查范围，不是三套固定检测规则。

### 0.5 三种“跨”的准确含义

#### 跨文件

围绕未知文件继续追踪：

- 创建或下载它的脚本和进程。
- 它释放、执行、读取、修改、重命名或删除的其他文件。
- 指向它的 cron、systemd 和其他配置。
- 它生成的压缩包、暂存文件、勒索信和后续载荷。

#### 跨时间

- 向前追溯文件落地、下载、上传、登录和潜伏。
- 向后追踪执行、子进程、外联、持久化、窃取和破坏。
- 查询昨天、过去一周或保留期内的相同 Hash、路径、命令、账号、C2 和周期行为。

示例：

```text
今天的未知文件连接某个 C2
+ 昨天同一主机的另一可疑文件使用相同 C2
+ 两者具有相似启动来源
→ 形成跨时间的持续后门候选路径
```

#### 跨主机

当发现远程登录、共享账号、相同 Hash、相同 C2、相同 SSH key、相同镜像、共享存储或多主机同步行为时，扩展到相关主机继续调查。

不是每个案件都默认查询全部历史和所有主机；只有出现跨域线索时才按需扩展。

### 0.6 当前已确认的输入

#### `T_FILE_DETAILS` 或等价 JSON

已知可提供：

- 文件 Hash、路径、类型、大小和权限。
- 文件创建、修改、访问、发现时间。
- 文件属主和 UID/GID。
- 触发进程、PID、PPID、UID/EUID、进程创建时间。
- `DETAIL` 回溯进程链。
- 用户、访问 IP、登录账号。
- 资产、主机、Pod、容器。
- 落盘/进程启动类型。
- HOFS 样本引用。

#### `T_PROCESS_CHAIN_HASH` 或等价 JSON

已知可提供：

- 进程链文件 Hash。
- Hash 信誉。
- PID 和进程名。

#### `T_abnormal_event_TO_REPORT_OS` 或等价 JSON

已知可提供：

- 异常事件和文件/进程上下文。
- IP、端口、攻击阶段和状态。
- 发生、检测、最近、上报时间。
- 用户、登录、主机、Pod。
- 上游置信度、次数和持续时间。

这些数据是 Agent 已确认的初始输入，不需要重复采集。但必须确认：

- 字段来自原始采集、快照、聚合还是算法推断。
- `DETAIL` 的顺序、完整性和回溯范围。
- 文件时间是元数据还是运行时事件。
- 网络字段能否绑定到目标进程。
- 表数据保留期和历史、跨主机查询能力。
- 是否能返回原始事件引用。

### 0.7 补充输入按三层组织

#### 终端系统层

回答“未知文件在真实 Linux 环境是否执行、做了什么”：

- 稳定主机、Boot、进程和容器身份。
- 进程创建和执行、父子关系、命令行、用户和会话。
- 文件 create/read/write/rename/chmod/chown/delete/execute。
- SSH、PAM、sudo、账号、组、密钥和权限变化。
- systemd、cron、at、启动配置和服务启停。
- 动态链接器、内核模块、挂载、备份、快照和共享存储。
- 容器、Pod、镜像、宿主 PID 和挂载关系。
- Web、数据库、发布、备份和合法运维记录。
- 文件操作速率、影响目录数、磁盘 I/O 等行为聚合。

#### 网络传输层

回答“相关进程与谁通信，是否 C2、外传或跨主机”：

- 带进程归属的 connect、listen、accept 和 close。
- DNS 请求和响应。
- 五元组、方向、持续时间、收发字节。
- HTTP/HTTPS、TLS、代理、防火墙、IDS/IPS、WAF。
- SSH、SCP、SFTP、NetFlow。
- 云和对象存储访问。
- PCAP 作为条件增强，不作为一期必需。

#### 静态与二进制结构层

回答“未知文件是什么、可能具备什么能力”：

- 优先开放 CDE 和现有算法的结构化输出。
- 通用文件元数据、Hash、样本引用、包归属和签名。
- ELF 架构、入口、段、节、依赖、符号、字符串、加壳和混淆。
- 脚本语言、解释器、编码、命令、文件、网络、持久化和外传线索。
- 每个静态发现的偏移、函数、行号或原始引用。

静态层只产生调查线索；终端层验证真实行为；网络层验证真实通信和传输。

### 0.8 数据开放原则

不是把所有数据一次性塞入模型上下文，而是：

> 在三个场景和授权范围内，将全部有用的数据能力告诉 Agent。Agent 根据当前案件和每一步结果判断是否需要读取；需要时能够按需获取。

产品侧需要提供证据能力目录：

- 有哪些数据源。
- 每种数据能回答什么。
- 支持哪些查询条件、时间和主机范围。
- 保留时间、完整性、延迟和采集盲区。
- 权限范围。
- 原始证据引用方式。

本项目不设计通用底层基座。RAG、领域模型平台、Skill 平台、MCP 网关、模型服务、通用记忆、权限和审计视为外部公共能力。本项目只定义威胁研判业务需要什么数据、知识、查询能力和返回契约。

### 0.9 端到端初步方案

```text
1. CDE/现有链路发现未知文件
2. 生成三张表记录或等价初始案件 JSON
3. Agent 建立未知文件、主机和告警时间锚点
4. 整理已知事实、候选假设、反证方向和证据缺口
5. 首先判断文件是否真实执行
6. 向前追溯来源、落地、登录和入口
7. 向后追踪子进程、文件、网络、权限和系统修改
8. 根据证据判断是否需要跨文件、扩时间或跨主机
9. 分别评估后门、数据窃取和勒索场景
10. 建立统一时间线和证据图
11. 生成已观察行为路径和候选攻击路径
12. 输出证据、反证、缺失数据、影响范围和 Verdict
```

Agent 的每一步由上一步结果驱动。例如：

```text
发现父进程是 php-fpm
→ 查询 Web/WAF 入口

发现读取 SSH 私钥
→ 查询后续跨主机认证

发现大文件归档
→ 查询归档进程及出站流量

发现高频文件改写
→ 查询服务、备份、快照和其他主机影响
```

### 0.10 输出需求

至少输出：

- 文件是否只落盘、被加载或真实执行。
- 执行前、执行中、执行后的行为路径。
- 主候选攻击路径和备选解释。
- 后门、数据窃取、勒索三个场景的支持状态。
- 跨文件、跨时间和跨主机关联。
- 带证据 ID 的时间线和事件图。
- 已观察、确定性关联、推断和未知的区分。
- 支持证据、反证和缺失证据。
- 数据覆盖和采集质量。
- 影响文件、账号、容器和主机。
- 案件级 Verdict、置信度和严重性。

### 0.11 可行性初步判断

总体可行，但结论质量取决于运行时证据。

已具备的可行性基础：

- CDE 已提供未知文件检测入口。
- 三张表已经提供文件、进程链、异常事件、用户、资产和容器等初始上下文。
- 现有样例 JSON、字段映射、Schema 和早期 Python MVP 可验证基础解析。
- Anthropic 安全 Skill 和公司攻击规则审计 Skill 可作为后续方法参考。

主要可行性约束：

- 若没有稳定进程执行事件，无法可靠证明文件运行。
- 若没有文件运行时事件，无法证明勒索加密和敏感数据访问。
- 若网络事件不能绑定进程，无法可靠证明后门 C2 或数据外传由目标文件产生。
- 若没有历史检索，无法完成真正的跨时间关联。
- 若没有统一主机身份和跨资产查询，无法完成跨主机分析。
- 若没有数据覆盖信息，“没有发现”不能作为强反证。

因此立项是否可行，不取决于大模型是否会分析，而取决于：

```text
现有三张表
+ 可补充的运行时遥测
+ 历史和跨主机查询能力
+ 可追溯的证据引用
```

## 1. 一句话定义

本项目要实现一个面向 Linux 未知文件场景的威胁智能研判 Agent：

> 当上游系统发现一个未知文件后，Agent 以未知文件路径、主机、告警时间和上游案件 JSON 为研判起点，在受控、只读、可审计的范围内主动获取和关联 Linux 主机、只读证据镜像、日志平台、网络设备及容器平台中的相关证据；分析未知文件在真实环境中的来源、落盘、执行及后续行为，还原带证据引用的行为路径和可能的攻击路径，最终判断该文件是否参与了真实攻击，并给出可解释、可追溯的威胁研判结论。

最终核心产出为：

```text
攻击路径
+ 证据链
+ 时间线与事件图
+ MITRE ATT&CK TTP
+ 反证与缺失证据
+ 数据质量说明
+ Verdict（案件最终研判）
```

未知文件不是结论，而是调查锚点。

## 2. 项目背景与边界

### 2.1 上游已有能力

公司已有系统负责：

- 向终端 Agent 下发扫描和防护任务。
- 通过 Kafka 等方式接收恶意文件、未知文件和异常进程信息。
- 文件列表、资产、任务及数据生命周期管理。
- 文件下载、解密、递归解压。
- 通过 JNI 调用 C++ CDE 引擎。
- 数据库匹配、启发式检测、压缩包分析。
- 黑文件、白文件、未知文件等初步分类。
- 将检测结果及已有上下文写入 `T_FILE_DETAILS`、`T_PROCESS_CHAIN_HASH`、`T_abnormal_event_TO_REPORT_OS` 等表或等价上游 JSON，其中已经包含一部分文件、触发进程、回溯进程链、用户、资产、容器、网络字段和异常事件信息。
- 上报、隔离和业务入库。

需要区分三个层次：

```text
CDE 引擎：
以静态文件检测为核心，完成文件特征分析和黑白灰/未知分类；
本身不持续采集和分析完整运行时行为。

现有检测与产品链路：
围绕检测结果保存并附带当前已经获取的文件、进程链、用户、
资产、容器、网络字段和异常事件等上下文，形成表记录或上游 JSON。

威胁智能研判 Agent：
首先消费上述已有表数据；当它们不足以回答跨文件、跨时间、
跨主机问题时，再通过授权工具按需查询补充证据并完成案件级推理。
```

因此，本项目从“文件已被现有系统判定为未知，并且已有一批表记录和上下文数据”开始，不重复实现文件发现、恶意性检测、黑白灰分类或已有攻击事件检测算法。

`T_FILE_DETAILS`、`T_PROCESS_CHAIN_HASH`、`T_abnormal_event_TO_REPORT_OS` 等表或等价 JSON 是本项目已经确认可利用的初始输入，不应被忽略或重复采集。即使本项目包含 ELF 或脚本本体分析，其目的也不是重新训练或替代恶意文件检测算法，而是从文件中提取可用于案件关联的命令、路径、IOC、持久化意图等线索，帮助 Agent 查询和解释真实环境证据。

但“表中存在某些运行上下文字段”不等于“已经具备完整运行时遥测”。仍需逐项确认：

- 字段由哪个组件产生，是实时采集、回溯快照、聚合告警还是推断结果。
- `DETAIL` 能否稳定提供完整进程祖先链，覆盖时间和丢失条件是什么。
- 网络字段只是某条异常事件中的 IP/端口，还是可以归因到目标进程的连续连接事件。
- 文件时间是文件系统元数据，还是包含创建、写入、重命名、删除和执行主体的事件流。
- 表是否支持按 Hash、路径、时间和主机进行历史及跨主机查询。
- 当前记录之外的数据是否仍可通过其他平台或采集接口补充。

### 2.2 项目负责什么

本项目负责现有算法完成检测之后的案件级智能研判。其重点不是再做一次检测，而是发挥 Agent 在开放式调查、上下文推理和工具编排方面的优势：

1. 理解上游表或等价 JSON 已经给出的文件结论、进程链、异常事件和主机、网络上下文。
2. 根据当前案件自动提出调查问题和多个候选解释，而不是仅执行固定字段规则。
3. 识别现有数据不能回答的关键问题，形成证据缺口。
4. 围绕未知文件路径主动选择 Linux 主机、只读镜像、日志、网络和容器证据源。
5. 动态调整时间窗口，并查询同路径、同哈希、同命令、同目标及历史周期证据。
6. 将分散的文件、进程、认证、网络、Web、容器和安全设备事件关联成具有时间与因果含义的行为链。
7. 同时寻找支持证据、反证和合法解释，避免把上游告警直接重复表述为攻击结论。
8. 区分事实、确定性关联、推断、未知和矛盾，说明结论边界。
9. 建立时间线、事件图和候选攻击路径，解释攻击如何发生、影响到哪里以及哪些环节仍缺证。
10. 输出案件级 Verdict，判断“这些已检测事件是否共同构成一次真实攻击”，而不是重新判断“该文件能否被算法识别为恶意文件”。

二者的职责边界可以概括为：

```text
现有检测链路：
由 CDE 完成静态文件检测和分类
+ 由产品链路保存文件、进程链、用户、资产、容器和异常事件上下文
+ 形成初始表记录或等价 JSON

威胁智能研判 Agent：
理解和组织已有表数据
+ 主动发现证据缺口并补证
+ 跨文件、跨时间和跨主机关联
+ 构建候选行为/攻击路径
+ 寻找反证与合法解释
+ 给出可解释、可追溯的案件级真实攻击判断
```

Agent 的价值不在于替换确定性检测算法，而在于处理无法预先写成一组固定规则的调查过程，并调用已有算法、查询接口和分析组件完成案件级闭环。

### 2.3 明确不做

- 不重新实现 CDE、JNI、Kafka、数据库业务和文件分类系统。
- 不设计或建设通用 Agent 底层基座，包括模型服务、RAG 平台、领域模型平台、Skill 注册与运行平台、MCP 网关、通用记忆、通用权限和审计基础设施。
- 底层基座视为外部公共能力；本项目只明确威胁研判 Agent 需要调用的业务知识、证据数据、分析能力和接口契约。
- 不实现 Windows 专属取证。
- 不做漏洞利用、攻击重放、红队或渗透测试。
- 不在普通主机上运行未知文件。
- 不自动访问样本中提取出的 URL、域名或 IP。
- 不做攻击组织或现实身份归因。
- 不因单个 IOC、可疑命令或 ATT&CK 标签直接判定攻击成立。
- 不让大模型不受约束地执行任意 Shell。
- 不直接修改、删除、隔离生产主机上的对象。
- 一期不要求接入所有生产系统，但必须验证主动调查闭环。

### 3.3 三类核心攻击场景（Linux）

项目聚焦未知勒索文件、未知劫持后门/远控和未知数据窃取/木马三个场景。这三类行为可能串联成一次完整攻击：攻击者先建立隐蔽访问并长期潜伏，再收集和外传数据，最后通过勒索破坏数据和业务。

#### 未知勒索攻击（ransomware）

Linux 环境需要重点分析：

- 对业务目录、用户目录、数据库文件、挂载卷和共享存储进行批量或高频读取、改写、重命名、删除和加密。
- 停止数据库、虚拟化、存储、备份、安全软件或其他关键 systemd 服务。
- 删除、破坏或禁用 LVM、Btrfs、ZFS、云盘、虚拟化平台或备份系统中的快照与恢复数据。
- 删除或覆盖本地备份目录，篡改备份任务、保留策略和恢复配置。
- 修改 systemd、cron、启动脚本、挂载配置、权限或文件属性，阻断服务启动和数据恢复。
- 在多个目录生成勒索信文本，或者修改 `/etc/motd`、登录提示、Web 页面等向管理员展示勒索信息。
- 在多个 Linux 主机、容器、Pod、挂载卷或共享存储上出现同步或相似破坏行为。

#### 未知劫持后门/远控（backdoor/C2）

Linux 环境需要重点分析：

- 使用异常进程名、伪装命令行、隐藏路径、删除后继续运行等方式隐藏进程和文件。
- 通过 `ptrace`、动态链接器劫持、`LD_PRELOAD`、共享库替换、内核模块或其他方式影响关键进程；这些行为必须由实际遥测证明，不能仅凭文件字符串推断。
- 通过 systemd service/timer、cron、at、SysV init、`rc.local`、Shell 启动文件、SSH `authorized_keys`、udev 或容器启动配置建立持久化。
- 创建异常账号、修改 sudo 权限、SSH 密钥或认证配置。
- 与未知外部 IP、域名或中继节点建立反向连接、周期回连、监听端口或远程控制通道。
- 使用 DNS 隧道、WebShell、代理或其他隐蔽通信方式进行命令与控制。
- 利用相同账号、密钥、文件、IOC 或远程连接继续影响其他 Linux 主机或容器。

#### 未知数据窃取/木马（data exfiltration）

Linux 环境需要重点分析：

- 静默枚举主机、用户、进程、网络、容器、挂载点、数据库和敏感目录。
- 批量读取业务数据、数据库文件、配置、源代码、日志和用户目录。
- 访问浏览器 Cookie、会话数据、账号密码、SSH 私钥、API Token、云凭据、证书和其他密钥文件。
- 在桌面 Linux 或终端场景中访问摄像头设备、输入设备、剪贴板或会话数据；是否构成录制或键盘记录必须由设备访问、进程和输出证据共同证明。
- 调用数据库导出、文件归集、归档、压缩或加密能力，将数据暂存在临时目录或隐藏路径。
- 通过 HTTPS、SCP/SFTP、代理、DNS、云存储或自定义协议向外部传输数据。
- 使用窃取的账号、密钥或 Token 访问其他主机、容器或云资源，继续收集数据。

三个场景是 Agent 的重点调查范围，不是三套固定检测规则。Agent 必须结合跨文件、跨时间、跨主机上下文，自主判断需要读取哪些证据，并同时分析攻击解释、合法解释、反证和数据缺口。

## 5. 核心定位变化：案件 JSON 是调查起点，不是全部输入

### 5.1 较早方案

较早方案假设上游把较完整的 `case_bundle.json` 一次性交给 Skill：

```text
完整案件 JSON
  -> 规范化
  -> 固定算法关联
  -> 攻击路径
  -> Verdict
```

该方案适合验证字段解析和关联算法，但不足以体现 Agent 优势：

- 上游没有提供的证据永远不会被看到。
- 无法根据文件类型和中间发现改变调查方向。
- 无法主动扩展时间窗口。
- 无法查询历史相似事件。
- 容易退化成固定 ETL 和规则打分程序。

### 5.2 当前确认方案

保留上游案件 JSON，但将其定义为“初始案情包”：

```text
案件 JSON + 未知文件路径 + 主机 + 告警时间
                      ↓
             Agent 读取已有事实
                      ↓
          形成假设、证据缺口和查询计划
                      ↓
     主动调用受控只读工具补充主机/镜像/网元证据
                      ↓
        确定性解析、关联、时间排序和建图
                      ↓
       攻击路径 + 证据链 + TTP + Verdict
```

Agent 的价值是决定：

- 当前最需要回答什么问题。
- 下一步查哪个证据源。
- 查询什么对象和时间范围。
- 中间结果是否要求扩窗或换调查分支。
- 哪个假设得到支持、被反驳或仍无法判断。
- 何时停止调查。

确定性代码的价值是：

- 日志解析。
- auditd 事件合并。
- PID、PPID 和进程实体关联。
- 时间转换与排序。
- 哈希比较。
- 去重和图结构生成。
- Schema 校验和规则门控。

两者不是替代关系，而是协作关系。

### 5.3 数据开放原则：能力开放、按需获取

“把所有可能数据告诉 Agent”不是把所有主机和平台的原始数据一次性放进模型上下文，而是：

> 在后门攻击、数据窃取和勒索三个场景的授权范围内，将所有可能有助于研判的数据源、可查询字段、覆盖范围和只读查询能力向 Agent 声明并开放。Agent 根据当前案件和每一步分析结果，自主判断是否需要读取某类数据；一旦决定读取，就能够通过受控工具获取对应证据。

因此，产品侧应提供“证据能力目录”，而不是预先替 Agent 固定一条调查流程。能力目录需要告诉 Agent：

- 有哪些数据源和查询工具。
- 每个数据源能够回答什么问题。
- 支持哪些查询条件、主机范围和时间范围。
- 数据保留时间、完整性、延迟和可能的采集盲区。
- 当前用户和案件被授权访问哪些主机、系统和敏感字段。
- 查询结果如何引用原始证据。

本项目只提出证据能力目录和业务调用诉求，不负责实现承载这些能力的 RAG、领域模型、Skill 平台或 MCP 基座。未来由底层基座负责知识检索和工具接入时，威胁研判 Agent 只需要按约定调用并消费返回结果。

运行时采用惰性、按需读取：

```text
Agent 知道全部可用证据能力
          ↓
根据当前案件判断下一步需要什么
          ↓
调用对应只读工具获取最相关的数据
          ↓
分析新证据并决定是否继续、换方向或跨主机扩展
```

这意味着：

- 不是上游只给哪些字段，Agent 就只能分析哪些字段。
- 不是固定流程规定必须依次读取所有日志。
- 不是一次性将所有日志全部塞入大模型。
- 不是允许 Agent 绕过授权任意读取生产数据。
- 是在授权的数据空间内，由 Agent 自主选择证据并推进调查。

三个场景限定的是 Agent 可调查的数据和安全知识范围，不是三套固定规则：

```text
后门场景相关能力：
进程、命令执行、网络回连、端口、账号、SSH、cron、systemd、
Web 日志、容器启动、跨主机同 IOC 和历史重复行为等。

数据窃取场景相关能力：
敏感文件访问、数据库导出、凭据读取、文件收集与压缩、暂存文件、
DNS/代理/流量、异常出站传输、跨主机数据访问等。

勒索场景相关能力：
批量文件访问和修改、文件重命名与删除、服务停止、备份和快照破坏、
挂载与共享存储、多主机扩散、勒索说明和业务影响等。
```

同一个数据源可以服务多个场景，同一个案件也可以同时涉及多个场景。Agent 应根据证据动态选择和组合这些能力，而不是在案件开始时被迫进入一条固定分支。

### 5.4 调查范围扩展原则：发现跨文件、跨时间或跨主机线索后再扩展

“跨文件、跨时间、跨主机分析”不是要求每个案件都默认读取所有文件、全部历史和所有主机，而是要求 Agent 具备条件式扩大调查范围的能力：

> Agent 先从 CDE 发现的未知文件、告警时间和当前主机开始。如果分析结果表明行为可能关联其他文件、其他时间段或其他主机，Agent 就以当前证据中的实体和时间为跳转线索，在授权范围内继续获取和分析对应上下文。

典型扩展方式：

```text
跨文件：
未知文件释放、下载、调用或修改了其他文件
→ 查询这些文件的内容、来源、执行及后续行为

跨时间：
当前行为可能由更早的落地、登录、潜伏、定时触发或历史活动引起，
或者在告警后继续产生外联、窃取、持久化和破坏
→ 动态扩大时间窗口并查询历史同类事件

跨主机：
发现远程登录、横向连接、共享账号、相同 IOC、相同文件、
相同命令、相同镜像或共享存储活动
→ 查询相关目标主机和历史事件
```

因此调查范围是动态形成的：

```text
单个未知文件
→ 当前主机局部行为
→ 相关文件和进程
→ 更早或更晚的关联行为
→ 相关容器或其他主机
→ 案件级行为/攻击路径
```

如果没有跨域证据，Agent 不应为了体现能力而无目的扩展。如果存在跨域线索但数据不开放、权限不足或遥测缺失，则应记录需要扩展的对象、原因和缺失证据，而不能假装完成跨域分析。

CDE 与 Agent 的能力差异可概括为：

```text
CDE：
在当前检测对象和已有规则覆盖范围内发现异常点。

Agent：
从异常点出发，根据每一步证据判断行为是否跨越文件、时间或主机；
若存在可能性，就沿实体关系主动扩大调查，直到形成案件级解释或确认缺证。
```

## 6. 最小启动输入

用户理想使用方式：

```text
“主机 web-01 在 2026-07-27 10:23 左右发生未知文件告警，
文件路径是 /tmp/.cache/update，请研判是否发生真实攻击并还原路径。”
```

### 6.1 必需输入

- `unknown_file_path`
- `host_id` 或可唯一定位资产的标识
- `incident_time`

### 6.2 强烈推荐

- `case_id`
- `timezone`
- 文件 SHA-256
- 文件类型
- 原始告警和规则名称
- `container_id`、Pod、namespace 等容器上下文
- 上游已有进程链和异常事件
- 可访问证据源及其保留时间

### 6.3 上游初始案件 JSON

建议最小结构：

```json
{
  "schema_version": "1.0",
  "case_id": "INC-001",
  "host": {
    "host_id": "web-01",
    "timezone": "Asia/Shanghai"
  },
  "incident_time": "2026-07-27T10:23:41+08:00",
  "unknown_file": {
    "path": "/tmp/.cache/update",
    "sha256": "example",
    "type": "ELF"
  },
  "alert": {
    "rule": "unknown_executable_created"
  },
  "available_evidence_sources": [],
  "provided_evidence": []
}
```

## 7. Agent 主动调查逻辑

### 7.1 调查循环

```text
1. 读取初始案件
2. 验证身份、时间和证据源覆盖
3. 建立初始时间窗口
4. 分析文件及已有证据
5. 生成候选假设
6. 识别可区分假设的证据缺口
7. 选择下一项安全只读查询
8. 获取、规范化并保存新证据
9. 更新实体、时间线、事件图和假设状态
10. 必要时扩展时间、历史、主机或容器范围
11. 满足停止条件
12. 输出最终调查报告
```

### 7.2 候选假设示例

- H1：文件由外部 Web 请求上传，并被 Web 服务执行。
- H2：文件由 SSH 登录用户上传或下载并执行。
- H3：文件由合法安装包、部署或运维任务生成。
- H4：文件来自容器镜像或部署过程，未在运行期写入。
- H5：文件已经落盘，但没有执行。
- H6：文件已执行，并产生网络连接、持久化或其他影响。

Agent 不应一开始只保留“攻击”一种解释，而应主动寻找支持证据和反证。

### 7.3 文件类型驱动的调查分支

ELF：

- 识别 ELF 头、架构、解释器、段、依赖、符号和字符串。
- 检查加壳、剥离、异常节区、可疑导入和嵌入 IOC。
- 查询 `execve`、进程实体、父子进程、文件描述符和网络连接。
- 查询复制、重命名、权限修改及持久化。

Shell/Python：

- 识别解释器和入口。
- 提取命令、路径、URL、域名、IP、端口和解码逻辑。
- 识别下载执行、反弹连接、清理日志、账户和持久化行为。
- 将提取出的对象转化为后续查询条件。

PHP/JSP/ASP/HTML：

- 识别 WebShell、命令执行、文件上传、动态加载和混淆。
- 查询 Web 访问日志、错误日志、应用日志和部署记录。
- 追踪 Web 服务进程到 Shell、下载工具和未知文件。
- 容器场景关联 Pod、镜像、挂载和 Kubernetes 审计。

### 7.4 动态时间窗口

初始可使用：

```text
T - 15 分钟 ～ T + 30 分钟
```

这只是缺省值，不是固定规则。扩窗触发条件包括：

- 文件创建或下载发生在窗口之前。
- 父登录会话更早开始。
- 进程或网络行为持续到窗口之后。
- 存在周期性触发。
- 同路径或同哈希历史事件需要进一步比较。

建议扩窗层级：

```text
局部：分钟级
案件：小时级
历史：7 天 / 30 天或产品保留范围
跨资产：同 IOC、同镜像、同账号或同攻击模式
```

停止条件：

- 已找到可信入口、执行链和影响证据。
- 连续多个扩展窗口没有新增高价值事实。
- 达到最大时间或查询预算。
- 数据源保留范围结束。
- 新查询无法再区分候选假设。
- 关键数据不可用，必须以证据不足结束。

### 7.5 历史和相似性检索

至少需要支持：

- 同 SHA-256、MD5、模糊哈希。
- 同完整路径、文件名、目录或 inode（条件允许时）。
- 同创建、重命名和执行命令。
- 同父进程、进程实体或解释器。
- 同 URL、域名、IP、端口和 DNS。
- 同登录账号、来源 IP、SSH key。
- 同 cron、systemd、Shell profile 或其他配置修改。
- 同 Pod、镜像、容器、namespace。
- 同一时刻、固定周期或相似时间模式。
- 同一主机和跨主机出现情况。

历史记录既可以成为攻击扩散证据，也可以成为合法运维反证。

## 8. 专项分析层详细需求

### 8.1 文件本体：静态分析

共同需求：

- 真实类型与扩展名一致性。
- SHA-256、MD5、大小、权限、属主、时间戳。
- 样本来源和安全存储引用。
- 签名、包管理归属和可信基线。
- 可疑字符串、IOC、路径和命令。
- 混淆、编码、压缩和未解析区域。
- 每个发现引用样本偏移、行号、函数或证据 ID。

静态分析只能说明文件“可能具备什么能力”，不能单独证明真实主机上已执行该行为。

### 8.2 文件本体：动态样本分析

一期不主动运行样本，只适配上游沙箱报告，例如：

- Cuckoo/CAPE 行为报告。
- 进程树。
- 文件操作。
- 网络连接和 DNS。
- 系统调用。
- 截图或行为标签。

动态沙箱中的行为仍需与真实主机证据区分：

```text
沙箱观察到行为 ≠ 真实案件主机已经发生该行为
```

### 8.3 进程与执行分析

要回答：

- 文件是否被 `execve` 或解释器真正执行。
- 进程稳定实体是谁，避免 PID 重用误关联。
- 父进程、祖先进程和子进程分别是谁。
- 完整命令行、工作目录、环境和用户身份。
- 是否发生 UID/EUID、capability 或 namespace 变化。
- 是 SSH、Web、容器、systemd、cron 还是人工 Shell 触发。

核心证据：

- auditd `SYSCALL`、`EXECVE`、`PATH`、`CWD`、`PROCTITLE`。
- EDR/HIDS/eBPF 进程事件。
- journald 结构化事件。
- 在线 `/proc/<pid>/`。
- 进程记账数据。
- 上游 `DETAIL` 进程链。

### 8.4 文件活动分析

要回答：

- 文件何时、由谁创建。
- 是否由下载、上传、解压、复制或重命名产生。
- 是否发生写入、chmod、chown、删除和执行。
- 执行后生成或修改了哪些文件。
- 是否写入 Web 目录、临时目录、系统配置或持久化位置。

需要区分：

```text
发现文件
文件落盘
文件被修改
文件可执行权限被设置
文件被加载
文件被执行
文件被删除
```

### 8.5 认证与用户分析

要回答：

- 相关用户和登录会话是否合法。
- 是否存在 SSH、sudo、su、PAM 或服务账号活动。
- 登录来源 IP 和认证方式是什么。
- 是否新建用户、修改组、密码、sudoers 或 authorized_keys。
- 相关行为是否符合历史基线。

来源：

- `/var/log/auth.log`
- `/var/log/secure`
- journald
- auditd
- `/etc/passwd`、`/etc/shadow` 元数据、`/etc/group`
- sudo 配置和日志
- SSH 配置和密钥元数据
- Shell history（仅作辅助，不能作为完整可靠证据）

### 8.6 系统日志分析

重点：

- systemd service 启停。
- 内核、崩溃、OOM、挂载和设备事件。
- 安全产品和应用错误。
- 审计服务是否中断或丢失事件。
- 主机重启和 Boot ID 对时间线的影响。

`sysmd` 是误写，正确名称为 `systemd`。

### 8.7 系统配置与账号分析

包括：

- 软件包归属、安装和升级记录。
- 主机身份、时区、NTP 和 Boot ID。
- 用户、组、sudo、SSH 配置。
- 服务、启动项、动态链接器和内核模块。
- 文件能力、SUID/SGID。
- 与 CMDB、发布、变更和合法基线比较。

该部分对建立反证很重要：未知不一定恶意，可能是合法安装、发布或运维产生的新文件。

### 8.8 Linux 持久化分析

一期至少覆盖：

- cron、crontab、anacron、at。
- systemd service、timer 和生成器。
- SysV init、`rc.local`。
- `.bashrc`、`.profile` 等 Shell 启动文件。
- SSH `authorized_keys`。
- `LD_PRELOAD` 和动态链接器配置。
- 用户、组、sudoers 和启动脚本。
- SUID/SGID 和 file capabilities。
- udev、内核模块和容器启动配置。

证据强度必须分级：

```text
发现可疑持久化配置
< 配置明确指向未知文件
< 配置实际触发未知文件执行
```

### 8.9 网络行为分析

要回答：

- 未知文件或其进程是否建立连接。
- 连接方向、协议、IP、域名、端口和时间。
- 网络行为是否能绑定到进程实体。
- 是否存在 DNS、代理、TLS、流量或周期性回连。
- 主机侧与防火墙、WAF、IDS/IPS、NetFlow 是否互相印证。

优先级：

```text
带进程归属的连接事件
> 主机连接事件
> 五元组流记录
> 聚合告警
```

PCAP 是条件增强项，不应成为一期必需输入。

### 8.10 容器环境分析

需要：

- 容器 ID、Pod UID、namespace、镜像和镜像摘要。
- 容器进程与宿主 PID 映射。
- 容器启动命令、环境、挂载、权限和 capability。
- 容器日志和 runtime 日志。
- Kubernetes API 事件和审计日志。
- 容器文件层与镜像基线差异。
- 文件来自镜像、挂载卷还是容器运行期写入。
- 是否存在逃逸或宿主影响证据；没有证据时不得推断。

## 9. 关键证据源和作用

完整字段和文件清单见：

- `docs/evidence_collection_requirements.md`

本节保留交接所需摘要。

| 证据源 | 主要作用 | 重要限制 |
| --- | --- | --- |
| auditd | 执行、文件、权限、账号和系统调用证据 | 需合并同一事件的多类记录；规则未配置则可能没有证据 |
| journald | 服务、系统、应用、内核和结构化上下文 | 建议由 `journalctl` 或接口导出，不直接解析二进制文件 |
| auth.log/secure | SSH、sudo、su、PAM 认证 | 发行版路径不同，可能轮转或转发 |
| syslog/messages | 通用系统和服务事件 | 内容依赖 rsyslog/syslog 配置 |
| `/proc/<pid>` | 在线进程、命令、环境、FD、命名空间 | 瞬时、敏感；进程结束后消失 |
| EDR/HIDS/eBPF | 稳定进程、文件和网络遥测 | 字段、覆盖和保留期需产品确认 |
| Web 日志 | Web 请求、上传、利用入口关联 | 需统一反向代理、应用和容器时间 |
| 网络设备/平台 | 防火墙、WAF、IDS/IPS、DNS、代理和流量 | 进程归属通常较弱，需要和主机证据关联 |
| 容器/K8s | 镜像、Pod、运行时和 API 行为 | 容器 ID、Pod UID 与宿主实体映射是关键 |
| 软件包/发布记录 | 合法来源与反证 | 必须能定位版本、时间和变更主体 |
| 文件系统镜像 | 离线文件、配置和日志痕迹 | 没有实时 `/proc`；时间戳可能受复制影响 |

auditd 重点文件：

```text
/var/log/audit/audit.log*
/etc/audit/auditd.conf
/etc/audit/audit.rules
/etc/audit/rules.d/*.rules
```

journald 常见存储：

```text
/var/log/journal
/run/log/journal
```

建议保留字段：

```text
__REALTIME_TIMESTAMP
_BOOT_ID
_MACHINE_ID
_PID
_UID
_EXE
_CMDLINE
_SYSTEMD_UNIT
MESSAGE
```

## 10. 只读工具层设计

Agent 主动调查不等于自由执行命令。推荐提供参数化、白名单、只读工具：

```text
inspect_file(path_or_sample_ref)
get_file_metadata(host, path, time)
query_process_events(host, start, end, filters)
query_process_ancestry(process_entity_id)
query_file_events(host, path_or_inode, start, end)

每个工具必须：

- 不能执行未知样本。

建议工具返回统一信封：

  "coverage": {},
  "items": [],
  "warnings": [],
  "raw_references": []
}
```

## 11. 最小证据模型

虽然一期暂不建设完整共享基础层，但至少需要：

```json
{
  "evidence_id": "E-001",
  "evidence_type": "process_exec",
  "source": "auditd",
  "source_event_id": "audit:1234.56:789",
  "observed_at": "2026-07-27T10:20:01.123+08:00",
  "host_id": "web-01",
  "container_id": null,
  "entities": [],
  "attributes": {},
  "raw_reference": {},
  "reliability": "high",
  "observation_status": "observed"
}
```

缺失语义必须区分：

- `not_observed`：在覆盖有效的数据中没有观察到。
- `not_collected`：相应遥测没有采集。
- `not_available`：数据原本可能存在，但当前不可用或已过期。
- `not_attributable`：观察到事件，但无法绑定到目标实体。
- `conflicting`：不同来源相互冲突。

“没看到”不能自动解释为“没有发生”。

## 12. 多源关联和攻击路径重建

### 12.1 关联键

强关联键：

- 稳定进程实体 ID。
- 主机 ID + PID + 进程启动时间。
- audit event serial。
- 文件哈希。
- 容器 ID、Pod UID、镜像摘要。
- inode + filesystem/device（条件允许时）。
- 网络 socket/process attribution。

辅助关联键：

- 路径。
- 命令行。
- 用户和会话。
- IP、端口和时间。
- 文件名、进程名和时间邻近。

只使用 PID、文件名或时间邻近属于弱关联，必须降低置信度并标注歧义。

### 12.2 统一时间线

必须：

- 明确时区。
- 保留原始时间和标准化时间。
- 处理秒、毫秒、微秒和纳秒单位。
- 记录主机时钟漂移。
- 使用 Boot ID 区分重启前后。
- 对时间不精确的来源记录误差范围。

### 12.3 事件图

节点可包括：

- 文件
- 进程
- 用户
- 登录会话
- 主机
- 容器/Pod/镜像
- IP/域名/URL
- 配置项
- 服务和计划任务
- 告警和原始事件

边可包括：

- `created`
- `modified`
- `executed`
- `spawned`
- `connected_to`
- `authenticated_as`
- `downloaded`
- `uploaded`
- `renamed`
- `configured_persistence`
- `triggered`
- `contained_in`
- `mounted_from`
- `correlated_with`

每条边至少包含：

```text
edge_id
source_node
target_node
relation
time
evidence_ids
relation_status
confidence
alternative_explanations
```

`relation_status` 建议：

- `observed`
- `correlated`
- `inferred`
- `unknown`

### 12.4 候选路径而非强行拼接

证据可能支持多条解释：

```text
候选路径 A：Web 上传 -> php-fpm -> sh -> 未知 ELF
候选路径 B：合法部署 -> 发布脚本 -> 未知 ELF
```

Agent 应比较支持证据、反证、缺失步骤和数据覆盖，不能把时间接近的所有事件拼成唯一攻击故事。

## 13. Verdict 定义

Verdict 是案件级最终研判，不是文件类型、恶意标签、ATT&CK 映射或风险分数。

建议枚举：

```text
confirmed_attack
likely_attack
suspicious_unconfirmed
likely_benign
insufficient_evidence
```

需要与以下概念分离：

- `confidence`：结论可信程度。
- `severity`：若结论成立，影响有多严重。
- `file_status`：文件黑白灰或未知状态。
- `ttp`：观察到的行为模式。

高可信攻击通常需要跨阶段、跨来源证据，例如：

```text
入口或来源证据
+ 实际执行证据
+ 执行后行为或影响证据
```

单独出现 `/tmp`、root、Shell、IOC 或某个 ATT&CK 技术，不能确认攻击。

Verdict 输出建议：

```json
{
  "result": "likely_attack",
  "confidence": 0.82,
  "severity": "high",
  "reasons": [],
  "counter_evidence": [],
  "missing_evidence": [],
  "data_quality_effect": []
}
```

## 14. 五类正式 Skill 产出

### 14.1 `reconstruct-unknown-file-attack-path`

核心案件 Skill。

职责：

- 接收初始案件。
- 编排主动调查。
- 合并各专项分析结果。
- 建立时间线和事件图。
- 生成候选攻击路径。
- 输出证据链、反证、缺失证据和 Verdict。

### 14.2 `analyze-unknown-scripts`

公司脚本解析 Skill 的适配目标，目前原件尚未拿到。

职责：

- 分析 Shell、Python、PHP、JSP 等脚本。
- 处理编码、解码、压缩和混淆。
- 提取命令、文件、网络、持久化和 IOC。
- 为每项行为提供代码位置和置信度。
- 将结果变成可供调查工具查询的线索。

### 14.3 `analyze-linux-persistence`

职责：

- 分析 cron、systemd、SSH key、启动文件、动态链接器、SUID 等。
- 关联配置内容、目标文件、时间、用户及实际触发事件。
- 区分“存在配置”“指向未知文件”“实际触发”。

### 14.4 `map-evidence-to-mitre-attack`

职责：

- 将已被证据支持的行为映射到 tactic、technique 和 sub-technique。
- 每个映射引用证据 ID 和映射理由。

约束：

- 不能凭关键词直接映射。
- TTP 不单独形成恶意结论。
- 不做攻击组织归因。

### 14.5 `audit-detection-bypass-coverage`

来源为已有 `attack-rule-auditor`。

## 19. 当前已确认结论

1. 项目只面向 Linux。
2. 上游未知文件分类系统继续保留，本项目不重复分类。
3. 未知文件是调查锚点，不等于恶意。
4. 上游案件 JSON 必须继续提供，但仅作为初始案情包。
5. Agent 应能主动在受控证据源中补充证据。
6. 主动调查必须通过只读、参数化、可审计工具完成。
7. 大模型负责调查规划和假设更新，确定性代码负责解析、关联、时间和建图。
8. 动态行为一期以适配已有沙箱报告为主，不主动运行未知样本。
9. 主机真实遥测是案件路径的主要证据。
10. 历史和相似性检索是 Agent 能力的重要组成部分。
11. 动态时间窗口必须有触发条件、预算和停止条件。
12. 文件本体、案件证据和案件重建是三个不同层次。
13. 主机痕迹属于案件证据分析层。
14. Verdict 是案件级结论，必须与置信度、严重性、文件状态和 TTP 分开。
15. 必须保留反证、缺失证据和数据质量。
16. 时间接近不能自动视为因果。
17. “未观察到”不能自动视为“没有发生”。
18. 持久化配置存在、指向文件和实际触发是三个不同证据强度。
19. 攻击绕过 Skill 属于离线检测质量保障，不是运行时案件路径。
20. 一期可跳过通用共享基础平台，但不能跳过最小证据契约。

## 21. 主要风险

| 风险 | 后果 | 建议 |
| --- | --- | --- |
| 证据源不足 | 无法证明执行或来源 | 明确输出缺失类型和 `insufficient_evidence` |
| PID 重用 | 错误拼接进程链 | 使用启动时间或稳定进程实体 |
| 时间漂移 | 错误时间线 | 保留时区、Boot ID、NTP 和误差 |
| 日志重复 | 同一事实被重复加权 | 做来源血缘和事件去重 |
| 只有告警摘要 | 无法审计结论 | 要求原始引用或降置信度 |
| Agent 任意查询 | 性能、安全和隐私风险 | 白名单参数化工具和查询预算 |
| Agent 任意执行命令 | 可能执行恶意样本或破坏主机 | 禁止任意 Shell，动态行为交沙箱 |
| 把沙箱行为当现场事实 | 生成错误攻击路径 | 明确证据环境 |
| 把时间接近当因果 | 编造攻击故事 | 图边必须引用关系证据 |
| 只寻找攻击证据 | 良性误报 | 强制候选假设和反证检索 |
| 无限扩窗 | 查询失控 | 分层窗口、成本和停止条件 |
| 模型受恶意文本影响 | 调查指令被样本篡改 | 把日志和样本视为不可信数据，不作为系统指令 |

## 22. 一期验收标准

一期不是“能生成一段安全分析文字”就算完成。至少应满足：

1. 能用最小案件输入启动调查。
2. 不会启动时直接加载全部证据。
3. 能说明当前已知事实和缺失证据。
4. 能提出两个以上合理候选解释。
5. 能选择与假设相关的只读查询。
6. 能根据结果扩展或收缩时间窗口。
7. 能完成至少一种历史或相似性检索。
8. 能从主机证据证明或否定文件执行。
9. 能建立带证据 ID 的时间线和事件图。
10. 能区分 observed、correlated、inferred 和 unknown。
11. 能输出主路径和备选解释。
12. 能输出反证和缺失证据。
13. 数据不完整时不会编造攻击链。
14. 能在良性案例中输出 `likely_benign`。
15. 能在证据不足案例中输出 `insufficient_evidence`。
16. 能记录 Agent 的查询过程和停止理由。
17. 所有未知文件分析均不在普通主机上执行样本。

## 25. 最终统一表述

本项目最终不是一个只对固定 JSON 执行攻击路径算法的程序，也不是一个可以自由登录主机执行命令的大模型。

它应是：

> 以未知文件案件 JSON 为初始调查材料，以 Linux 主机、只读镜像、容器和网元证据为调查空间，以参数化只读工具为行动边界，以确定性解析和事件图算法为可信底座，以 Agent 的假设驱动调查、动态扩窗和历史检索能力为核心优势，最终输出可审计攻击路径和案件 Verdict 的安全调查系统。
