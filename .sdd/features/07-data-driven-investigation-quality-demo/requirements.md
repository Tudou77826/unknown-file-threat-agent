# Data-Driven Investigation Quality Demo Requirements

## 1. 目标

在没有生产数据底座的条件下，建设可重复的参考数据环境，直观展示：固定 Agent、模型、规则和预算时，数据源种类、Coverage 和反证能力如何改变可回答问题、研判结论与处置质量。

同时将项目所需的部署与运行配置统一从代码和启动脚本提取到项目根目录 `.env`，通过类型化配置对象加载和校验。

## 2. 必须满足

### 对照实验

- 同一基础案件在不同实验组中必须使用相同告警、Agent 版本、规划器、规则、工具目录和预算。
- 实验组只能改变可用数据源、Coverage 或资产上下文，不得通过修改期望结果影响研判。
- 至少提供恶意和合法运维两类基础案件，分别验证攻击确认和误报排除。
- 每类案件至少覆盖 L0 告警级、L1 执行级、L2 行为级和 L3 决策级四个数据等级。
- 数据必须标记为参考数据，不得暗示其来自生产环境。

### 参考数据底座

- 提供统一的告警、Evidence、Entity、Relation、Coverage 和资产上下文存储。
- Agent 只能通过现有 Port 查询参考数据，不得识别或依赖演示目录结构。
- 每条 Evidence 必须保留来源、时间、主体引用和可追溯原始记录标识。
- 数据 Profile 必须显式声明可见数据源、Coverage 和不可用原因。
- 数据生成和导入必须可重复，相同版本与随机种子产生相同结果。

### 数据就绪度

- 输出结构化 `DataReadinessReport`，至少包含可用数据源、缺失数据源、可回答问题、受阻问题、Coverage 和建议补充的数据能力。
- 数据就绪度由确定性规则计算，LLM 不得自行提高数据完整性或把 Knowledge 当作 Evidence。
- 报告必须解释数据缺失对执行确认、行为归因、威胁确认、反证和处置决策的具体影响。

### 处置上下文

- 提供参考资产目录并通过 `ResponseContextPort` 查询。
- 资产上下文至少包含环境、业务系统、重要性、负责人、维护窗口、隔离策略和隔离影响。
- 同一研判结论在不同资产上下文下可以产生不同处置建议，但不得改变已经发布的研判事实。

### 配置外置

- 项目所需的部署和运行配置统一从根目录 `.env` 加载，进程环境变量和 CLI 显式参数可以覆盖。
- 模型、双循环预算、图运行、数据底座、Checkpoint、展示服务和输出路径均纳入类型化配置。
- 缺失、非法或相互冲突的配置必须在启动阶段失败，不得运行到业务节点后再报错。
- 提供不含密钥的 `.env.example`，实际 `.env` 继续由 Git 忽略。
- 领域判定规则、证据门槛、工具评分权重、案件输入和人工审批决定不得移入 `.env`。

### 展示

- 展示同一案件在四个数据等级下的结论变化和新增可验证事实。
- 展示数据源 Coverage 矩阵、受阻问题、证据链、反证、处置建议和资产影响。
- 展示必须区分“数据不可用”“查询为空”“证据反驳”和“尚未调查”。

## 3. 非目标

- 证明生产环境准确率、召回率、时延或容量。
- 建设生产数据湖、实时流处理或多租户数据平台。
- 接入真实 EDR、SIEM、CMDB、SOAR 或身份系统。
- 实现 RAG、Embedding、向量索引或知识评测。
- 自动执行隔离、封禁、删除等处置动作。
- 把安全规则和研判政策改造成可由运维人员任意修改的环境变量。

## 4. 验收条件

- 固定引擎条件下，仅切换数据 Profile 即可完成 L0 至 L3 对照实验。
- 恶意案件随关键数据补齐形成可追溯攻击链；合法案件随反证补齐降低误报风险。
- 数据不足时系统保持 `insufficient_evidence` 或受限结论，并明确指出阻塞数据源。
- 四个等级均生成 `DataReadinessReport`、`JudgmentResult`、`ResponsePlan` 和 `CaseReadModel`。
- 所有运行配置可由根目录 `.env` 提供，代码中不存在重复的部署参数默认值。
- `.env.example` 能支持离线确定性 Demo，且不包含真实凭据。
- 现有黄金 Case、Checkpoint、双循环、契约和架构依赖测试不退化。
