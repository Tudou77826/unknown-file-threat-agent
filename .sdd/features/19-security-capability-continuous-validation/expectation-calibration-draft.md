## 逐案例三步清单（已评测 5 例）

### c2-malicious-elf（手写基准，维持确认恶意）

- ① 来源：手写参考数据，非真实靶场执行证明。数据描述隐藏路径 ELF 的 root 执行、
  多次连接、systemd 写入/启用/启动，以及目标进程派生 shell 执行命令。
- ② AI 可见（16 事件）：执行(锚点) + 父链×3 + 网络×4 + socket 收发×2 +
  systemd 写入/启用×3 + 反证×2（包不归属、端点未批准）
- ③ 提案：**confirmed_malicious（维持基准目标，修复后复跑）**。上述组合比靶场四条事件支持更明确的判断。
  socket 收发只报告方向和字节数，不能单独证明收到命令或回传命令结果。

### c2-benign-baseline（手写基准，维持良性）

- ① 来源：手写参考数据，描述厂商监控代理随 systemd 服务运行、回连批准端点
- ② AI 可见：包归属有效 + 端点批准 + 执行 + 服务事件
- ③ 提案：**benign（维持）**。

### t1105 工具传输（决策点 A：建议可疑）

- ① 事实（已修正）：file:// 本地协议复制落地（无外部网络传输）+ chmod + root 执行 +
  单次回连本机模拟端口 127.0.0.1:8443
- ② AI 可见（当前 4 事件）：执行(hash 锚点) + 网络×1 + 包不归属 + 端点未批准；
  补采后预期新增：文件写入事件
- ③ 提案：**suspicious**。无包归属、root 执行、本机连接和文件落地不足以证明恶意。
  当前端点记录由空清单生成，不能作为未经批准的证明；本机连接不能称为外连。
  单独补上文件写入不自动升级为倾向恶意。若要验证外部工具传输，需要真实执行传输后重新采集。

### t1053 cron / t1037 rc.local（决策点 B：当前建议可疑，补采后另校准）

- ① 事实（已修正）：写入 /etc/cron.d 或追加 rc.local（周期执行/自启未实际发生，
  载荷为手动触发一次）+ 单次回连
- ② AI 可见（当前各 4 事件，文件写入丢失）：执行 + 网络×1 + 双反证；
  补采后预期新增：/etc/cron.d、/etc/rc.d/rc.local 的写入事件
- ③ 提案：当前四条事件对应 **suspicious**。不批准将“启动项写入 + root 执行 + 本机连接”固定为确认标准。
  补采的路径写入记录只证明发生了写入；如需证明启动项指向目标 ELF，要有任务内容或明确关联记录。
  若有明确未经授权信息及目标关联，再评估倾向恶意；确认恶意需要能够排除合理正常解释的恶意行为证据。
  保留补采前后对照，观察结论与依据的变化，不要求补齐后必须确认。
  旧验收结果保留并标注采集缺口，不直接改成通过，也不在对照完成前认定原因只在采集。

## 系统性注记

- **端点批准**：空清单、缺清单或完整性不明，应表示未知；不能统一生成 approved=false。
  有实际批准记录才表示已批准；有明确禁止记录，或经确认完整且适用的清单排除该端点，才能表示未批准。
  如现有格式不能表示未知，则不生成否定记录，另记基线缺失。
  实验端点基线按实际用途在运行前确定，不能按恶意/良性标签倒推；不能把所有本机端点一概视为安全。
- **包归属**：settle_case.py 目前把包归属结果同时写入 signature_valid 和 repository_trusted，
  但没有进行签名或仓库可信检查。这两项不得从包归属推导；未检查应省略或表示未知。
  包归属查询失败也应表示未知，不能解释为已证明无归属。
