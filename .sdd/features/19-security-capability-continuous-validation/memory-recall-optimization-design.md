# 上下文归档与召回（Context Archive / Recall）——评测吞吐优化设计

状态：设计稿 v4（按评审意见修正：recall 的探查形态确立为独立上下文的 AI 问答并回到迭代 A 核心，删除确定性检索方案），待评审。
基线锚点：git tag `perf-baseline-v1`（18 案例均值 20 分钟/案、约 34 万 tokens/案、15/18 执行正常、方向正确率约 60%）。
上游依据：Feature 12（上下文管理）的前缀稳定与压缩定型约束；Feature 15（中间件基座）的 `create_agent` 中间件栈。本设计替换 F12"70% 触发 LLM 压缩"的主路径（其保留为兜底），不推翻其约束。

## 1. 问题定位

成本两个结构性放大点，均源于"作用已兑现的内容仍以全量形态摊在上下文里"：

1. **报告组装单次调用吃进全量账本**：`reporting.py::report_context` 全量 dump 账本，实测输入 55k–143k tokens，单案最大一次调用。
2. **规划循环逐轮全量重放**：历史随轮次线性累积、每轮重放，总量近似随轮数二次方增长；70% 窗口触发的 LLM 压缩本身又吃一次全历史。

原文一直都在（裁剪中间件保留 artifact 与类型化账本），可回收的是"上下文里同时摊开的数据量"。

## 2. 核心机制：两个通用原语

**archive（归档）的本质**：把一段大概率不会再起作用的上下文**移出窗口、存到外部**，在原位留下一张紧凑的卡（模型自写的摘要 + 确定性生成的事实附录）。

**recall（召回）的本质**：在归档区这个确定的上下文上做 **AI 问答**。主上下文提出问题，一个独立上下文的探查 AI 在归档内容里自行探查并给出带引用的答案——主上下文只接收答案，永不被归档原文重新膨胀。配套两个精确取回入口（按句柄展开、按 ID 取原文），服务"要原件不要答案"的场景。

与具体工作流解耦：本设计不规定"什么时候该归档"。以未知文件调查为例，一种自然的节奏是按推断线组织调查——看到现象、补充实测、形成推断、若干轮查证、得出结论（含排除）；一条线结论落定后，其查证细节大概率不再被逐字使用，正是归档的典型时机。但这只是引导性示例：工具对"归档什么"没有任何业务假设。

设计取舍（继承历轮评审结论）：

- 压的只是历史消息区间（模型思考 + 工具结果成对），系统提示与案件背景前缀永不压；
- 摘要由模型自己写（归档时自述，写给未来看不到细节的自己），事实附录由模板确定性生成——各干各的，事实部分零幻觉面；
- 卡片数量应当是个位数：机制上有最小区间护栏，观测上有卡片数指标；
- 逐块/逐轮的细粒度压缩被否定（v1 教训）：颗粒度是完整逻辑单元，由模型判断何时闭环；
- 归档区内的查找与问答由 AI 完成（v4 修正）：代码只做精确地址读取（句柄/ID），不做内容检索——匹配、同义、相关性判断是 AI 的本职，代码实现既复杂又无法保证质量。

## 3. 方案分层

| 层 | 机制 | 状态 |
| --- | --- | --- |
| 单条结果投影 | 现有 `ReducerMiddleware`（brief_result 字段投影），处理单条工具结果过大的问题 | **不变**（与归档正交） |
| 区间归档 | 新 `archive_context` 工具 + `ArchiveMiddleware`：模型主动归档，消息区间→卡片，原文入库 | **新增，本设计核心一** |
| 召回 | 新 `recall` 工具：`question` 独立上下文 AI 探查（核心二）+ `archives`/`ids` 精确取回 | 新增 |
| 报告组装 | 输入 = 案件背景 + 全部归档卡 + 未归档尾段 + 证据 ID 目录（现有 evidence_catalog），替代全量账本 dump | 修改 |
| 兜底 | 官方 `SummarizationMiddleware` 保留；归档节奏正常时预计不触发，其触发即"归档机制失效"的告警信号 | 不变 |

上下文稳态构成：系统提示 + 案件背景 + 个位数归档卡 + 当前活跃工作段。**上下文体积由"还没归档的部分"决定，与调查总轮数无关**。

## 4. 组件设计（文件级）

### 4.1 MemoryStore —— 新 `judgment/application/memory_store.py`

- **块粒度**：一次归档对应的完整消息区间快照为一个块；句柄 `arc-{k}` 递增。
- **索引**：activity_id / evidence_id / relation_id / query_id → 归档块 + 原始工具 payload 的**精确地址定位**（字典，全案 ID 规模百级）。索引只服务"按已知地址取原件"，不做内容检索。
- **原始 payload 来源**：消息 artifact 的 unreduced_content 与类型化账本（均已存在），库内存区间与引用。
- **生命周期**：run 作用域，由 `middleware_runtime` 创建，交给归档中间件、recall（探查与取回）与报告组装。

### 4.2 archive_context 工具 + ArchiveMiddleware —— 新 `agent_middleware/archive.py`

**工具本质**（接口详见附录 A）：把自上一归档点以来的消息区间（或 `from_round` 指定的起点至当前）移出上下文，原位留卡，返回句柄。

**卡片构成**：

- **摘要**：模型归档时自写的 `summary`——这段内容是什么、发生了什么、得出了什么，写给未来看不到细节的自己；
- **附录（确定性模板生成）**：区间覆盖的轮次范围、执行过的查询（工具+参数摘要）、各查询返回量与**负结果**、产生的全部可引用 ID、句柄。

**中间件机制**：

- 归档调用在工具执行后标记待归档区间，在下一次模型调用前完成重写：区间内 AIMessage（思考+tool_calls）与 ToolMessage **成对移除**（轮边界切割，结构上不可能切出半对），替换为一张卡片消息；原文区间序列化入 MemoryStore。
- **轮次锚定**：一个模型轮 = 一条 AIMessage 及其配对 ToolMessage，边界客观存在；每轮注入一行轮次标记（`[round 7]`，兼作 F12 进度投影），供 `from_round` 引用。
- **防滥用护栏**（确定性，与业务无关）：区间不足（默认 <2 个模型轮或 <1k tokens）时拒绝归档并返回当前区间量与门槛——逐轮细碎归档在此被挡掉；`from_round` 越界按默认区间处理并回显。
- **回显确认**：工具返回区间摘要（轮次范围、工具调用数、产生的 ID 数、负结果清单），模型下一轮即见切了什么，误切可 recall 完整找回。
- 归档调用计入 `max_tool_calls`；已归档区间不再改写（幂等，满足 F12 定型约束）。

### 4.3 recall 工具 —— 新 `bootstrap/memory_tools.py`

三种入口（互斥，混用拒绝）：

**① question——AI 探查（核心形态）**：在归档区这个确定上下文上做 AI 问答。

- **探查 Agent**：独立上下文的小型工具循环（复用 `create_agent` 基座 + 探查模型）：
  - 输入：问题 + 归档卡索引（全部卡片的摘要+句柄+轮次范围+ID 清单，天然很小）；
  - 自有工具：`open_archive(handle)` 展开某个归档的完整内容、`get_raw(id)` 取原始记录；
  - 自行决定看什么、看多深，直到能回答；
  - 契约：答案必须注明所依据的归档句柄与记录 ID；找不到就明说找不到；只回答问题，不复述无关内容。
- **边界**：单次探查 ≤4 次展开、循环 ≤8 步、答案 ≤800 tokens；每案探查 ≤6 次（超限显式拒绝并提示改用精确取回）。探查 token 单独事件计量。
- **答案详略策略（提示词控制）**：主模型提问即说明被压缩的内容实际被需要——探查答案**慷慨携带相关细节**，不只回答最小答案：与问题相关的字段值、时间、ID、伴随的负结果一并带回（"既然想看，就多带一些"）。详略由探查系统提示约束：围绕问题携带、不展开无关内容、上限内不截断关键事实。
- 主上下文只收到带引用的紧凑答案；探查过程及其展开的原文**永不进入主上下文**。
- 真实性约束：探查答案是二手提炼——系统提示与工具描述均注明"下结论的关键事实以按 ID 取回的原始记录为准"。

**② archives——按句柄展开**：把指定归档的完整细节（各轮思考原文 + 工具结果投影）**取回主上下文**。服务"要原件不要答案"的场景：终局复核自己当时的推理、需要亲自重看细节重新判断。单次 ≤2 个。

**③ ids——按 ID 取原文**：取指定记录的完整字段。单次合计 ≤3 条，未命中列入 `missing`，绝不编造。

设计说明：②③是精确地址读取——句柄和 ID 是已知地址，取原件不存在"检索"问题，代码做是最可靠且零成本的；一切"找内容"的工作（不记得句柄、跨归档找线索、相关性判断）全部归①的 AI 探查。

边界与预算：无 host_refs，边界策略天然放行；计入 `max_tool_calls`；单次上限内截断并提示分批，不静默丢弃。

### 4.4 报告输入重组 —— `reporting.py::report_context` v2

输入构成：案件背景 + 全部归档卡（摘要 + 附录）+ 未归档尾段投影 + `evidence_catalog`（现有 ID 白名单目录）+ 接地规则 instructions。

不变：`forced_structured` 链路、接地校验（仍对账本白名单做，不依赖 prompt 内容）、rejudge 的 `evidence_catalog`、`DeterministicFallbackBuilder`。

信息充分性论证：归档卡携带调查者全部阶段性结论与负结果；ID 级事实由 evidence_catalog 每-ID 摘要覆盖；报告引用合法性由账本校验保证。若实验显示信息不足，回退路径：rejudge pass 按校验问题涉及的 ID 注入对应原文块（利用现有机制，不动主链路）；必要时报告前允许一次探查式证据整理（独立上下文消化全账本产出证据简报）——回退选项，不进 v1 主链路。

### 4.5 提示词增补 —— `data_tool_planner.py`

PLANNER_SYSTEM_PROMPT 增补记忆契约（引导，非强制）：

- 上下文是工作内存，归档区是长期记忆；一段内容的作用兑现后（结论落定、方向排除、背景确认），它大概率不再被逐字使用——归档它，给未来的自己留一段自含的摘要；
- 典型节奏示例（非规定）：一条推断的查证得出结论（含排除）时归档该段；切换新方向前先收束旧方向；
- 需要细节时用 recall：问一个问题让探查去查；要亲自重看用句柄展开；要证据原文用 ID 取回；关键事实以原始记录为准；
- 摘要写给未来看不到细节的自己——写得含糊，未来就得多花一次探查。

### 4.6 配置 —— `settings.py`

`ARCHIVE_MIN_SPAN_ROUNDS`（默认 2）、`ARCHIVE_MIN_SPAN_TOKENS`（默认 1k）、`RECALL_MAX_ARCHIVES`（默认 2）、`RECALL_MAX_IDS`（默认 3）、`RECALL_PROBE_MODEL`（默认同判定模型）、`RECALL_PROBE_MAX_CALLS`（默认 6）、`RECALL_PROBE_MAX_OPENS`（默认 4）、`RECALL_PROBE_MAX_STEPS`（默认 8）、`RECALL_PROBE_ANSWER_MAX_TOKENS`（默认 800）。

## 6. 实验设计与防过拟合

- **Step 0 成分测量**：对基线 run 的账本与消息历史做成分统计（报告输入各集合占比；规划各轮输入曲线），校准归档阈值与召回上限。先测后改。
- **质量门**：demo 10 + validation 18，`--fresh` 全新重跑，epochs 同基线；五维指标任何一维不得低于基线。
- **新增观测**：每案归档次数与卡片数（守住个位数）、护栏拒绝次数、recall 三入口使用分布、探查次数/展开次数/每次探查 token（成本核算）、每轮上下文 token 曲线（验证"与轮数无关"）、报告输入 tokens。
- **通用性自审**：改动均 case 无关；参数全局统一；实验记录与自审追加至 `attack_lab/OPTIMIZATION_CHECKLIST.md`。
- **成功标准**：单案 ≤18 万 tokens（目标 12–15 万）、时长 ≤12 分钟、五维不降。探查成本计入总账。

## 7. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 模型不归档（节奏不成立），成本不降 | 提示词引导 + 兜底中间件不失控；归档次数进观测，实验门把关 |
| 模型过度/细碎归档，卡片泛滥 | 最小区间护栏（确定性拒绝）+ 卡片数观测 |
| 模型归档了仍在起作用的内容，反复 recall 折腾 | 观测 recall 频次与归档-recall 间隔；提示词强调"作用已兑现才归档"；单次上限控制回涨 |
| 探查答案幻觉/失真污染主上下文 | 答案强制附句柄与 ID 引用；二手性质双处注明；关键事实要求原始记录确认；每案次数与单次步数上限 |
| 探查成本失控 | 次数/展开/步数三重上限 + token 事件计量，实验门核算 |
| 摘要写得差（未来自己看不懂） | 提示词把摘要定位成"给未来的自己"；附录确定性兜底事实清单 |
| 报告信息不足 | evidence_catalog 每-ID 摘要兜底；回退：rejudge 注入 issue 涉及的原文块 |
| recall 重载后上下文回涨 | 单次上限 + 有界截断；重载内容随下一次归档自然收敛 |
| glm-5.3-flash 结构化输出失败面 | archive/recall 均为普通工具调用，不涉 schema；探查是普通文本问答，不涉 schema；报告链路不动 |

## 附录 A：工具接口规格（迭代 A）

### A.1 archive_context —— 归档一段上下文

**入参 schema（StrictModel，模型可见描述即契约）**

| 字段 | 类型 | 必填 | 约束 | 说明（模型读到的原文） |
| --- | --- | --- | --- | --- |
| summary | str | 是 | min_length=10 | 这段内容的摘要，写给未来看不到细节的你：这段做了什么、得到了什么（结论/排除/确认）、留下哪些关键线索。要自含依据 |
| from_round | int \| null | 否 | ≥1 | 归档区间默认自上一归档点起；需要只收走更早的某段时，用轮次标记指定起点 |

**工具描述（注册原文）**

> 把一段已经完成使命的上下文移出对话窗口：区间内的思考与工具结果会被收起，原位只保留你写的摘要与一份事实附录，原内容存入归档区、随时可用 recall 取回。何时使用由你判断——一段内容的作用已经兑现（结论落定、方向排除、背景确认），后续大概率只需摘要而不需逐字细节时，就归档它。区间默认是自上一归档点以来的全部；查证不足两个模型轮时会被拒绝（归档无收益）。成功后会回显实际归档的区间与内容清单，与预期不符时用 recall 找回。

**返回（成功）**

```json
{"archived": true, "archive_id": "arc-3",
 "round_span": [4, 9], "model_rounds": 6, "tool_calls": 6,
 "produced_ids": {"activities": 14, "evidence": 14, "relations": 2},
 "negative_results": ["query_network_activities(p26) 返回 0 行"],
 "message": "已归档 arc-3：第 4–9 轮、6 次工具调用、14 个活动 ID，recall 可展开"}
```

**返回（护栏拒绝）**

```json
{"archived": false, "reason": "span_too_small",
 "current_span": {"rounds": 1, "tokens": 480}, "min_required": {"rounds": 2, "tokens": 1000},
 "message": "区间过短，归档无收益；继续工作，待这段内容完成使命后再归档"}
```

### A.2 recall —— 查看归档内容

**入参 schema（三种入口互斥，混用拒绝）**

| 字段 | 类型 | 说明（模型读到的原文） |
| --- | --- | --- |
| question | str \| null | 提一个问题，由独立上下文的探查 AI 在归档区里自行查证并给出带引用的答案；不记得归档在哪、或只需要一个事实性答案时用这个 |
| archives | list[str] \| null | 按句柄展开归档（如 arc-3）：该段完整思考与查证过程取回你的上下文，供你亲自重看重新判断；单次最多 2 个 |
| ids | list[str] \| null | 按 ID 取原始记录（activity/evidence/relation）的完整字段；单次最多 3 条 |

**工具描述（注册原文）**

> 查看被归档的内容，三种方式任选其一：①提问题（question）——一个独立上下文的探查助手会在归档区里查找并回答，答案注明依据的归档与记录 ID；②按句柄展开（archives）——整段细节回到你的上下文，你亲自重看；③按 ID 取原文（ids）——取某条证据的完整字段。注意：探查答案是二手提炼，下结论的关键事实请以按 ID 取回的原始记录为准。

**返回（探查）**


### A.3 探查 Agent 契约（recall 内部实现，模型不可见）

- 上下文：系统提示（探查契约）+ 问题 + 归档卡索引（全部卡片的句柄/摘要/轮次范围/ID 清单）；
- 工具：`open_archive(handle)`、`get_raw(id)`（对 MemoryStore 的只读访问）；
- 契约：答案必须注明依据句柄与 ID；找不到明确说找不到；不回答问题外的内容；不做威胁判断（探查只查证事实，判断留给主模型）；**慷慨携带相关细节**——提问即意味着被压缩内容实际被需要，答案要带回问题相关的字段值、时间、ID 与伴随负结果，不只给最小答案，也不展开无关内容；
- 边界：单次 ≤4 次展开、≤8 步循环、答案 ≤800 tokens；实现复用 `create_agent` + recursion_limit。

### A.4 引导模型使用的方式

机制与引导分离：工具只承载本质（移出/取回/问答）与硬约束（区间下限、单次上限、三入口互斥）；何时用、怎么组织调查节奏，由 PLANNER_SYSTEM_PROMPT 的记忆契约段引导（见 4.5）。典型动作（提示词示例段）：

1. **收束**：一段查证得出结论（含排除）→ `archive_context(summary="…")` → 原位留卡；
2. **换向**：只收走旧方向 → `archive_context(summary="…", from_round=6)`；
3. **询问**：不记得细节在哪 → `recall(question="p26 的两次外连目的地是什么，是否在白名单")` → 得到带引用的答案；
4. **复核**：怀疑早前判断 → `recall(archives=["arc-2"])` 亲自重看；
5. **取证**：落关键证据 → `recall(ids=["act-12"])`，以原文为准。
