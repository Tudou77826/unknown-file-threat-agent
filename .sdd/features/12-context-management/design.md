# Context Management — Design

## 1. 现状

feature 11 实测暴露出 AI 调查"查全后仍反复探查"的失忆循环，根因是上下文管理缺失：

- 规划器唯一的"上下文管理"是 `data_tool_planner.py` 的一行 `for trace in state.tool_ledger.traces[-12:]`：把最近 12 条工具结果**原封不动**回放。
- 无压缩、无进度投影、无触发阈值；只按"条数"截断，截断语义错位。
- 7 个域查全后，第 13 条工具结果把最早的 `query_process_activities` 挤出窗口，模型"忘记已查该域"而回头重查。

同时，项目对**上下文窗口规格没有任何假设或配置**：`JUDGMENT_MODEL_MAX_TOKENS=4096` 是**输出上限**，不是窗口。

> 历史纠偏：本 Feature 第一版设计曾提出"摘要降级 + token 预算截断"，其中"摘要降级"被错误地实现为**无条件**字段抽取（`brief_result`），导致 `explore_entity` 的 relations 等有价值信息被静默丢弃。该方向已被否定，替换为本设计的"70% 触发 + LLM 压缩"。

## 2. 目标

1. 把**上下文窗口**作为模型资源配置项提取到配置，初始 100K，压缩据此动态触发。
2. 每轮给模型一个**结构化进度投影**（JSON），让它看见"自己做到哪了"。
3. **达到窗口 70% 时触发压缩**：用 **LLM** 把旧的工具历史浓缩成"调查进展摘要"，**尽可能保留有价值的信息**。
4. 保持**前缀一致性**：稳定前缀字节级不变，动态内容放尾部，压缩产物写入时定型。

## 3. 概念定义

一次发给大模型的内容，一共 4 块：

| 块 | 说明 | 是否变化 |
|---|---|---|
| ① 系统提示词 | 告诉模型"你是谁、调查规则" | 30 轮内一字不变 |
| ② 案件背景 | 案件编号、授权范围、涉案实体、告警线索 | 调查一开始定死，之后不变 |
| ③ 工具调用历史 | 模型查了哪些东西、每次拿到什么结果 | 每轮变长 |
| ④ 进度状态 | 本轮第几步、已查哪些领域、还剩哪些 | 每轮更新，仅一条 |

**触发口径**：以上 4 块**总长度**（估算 token）占上下文窗口的比例，达到 **70%** 时触发压缩。

**压缩对象**：只压第 ③ 块（工具调用历史）中**旧的部分**。①②固定不变不该压；④就一条压不掉。

## 4. 消息布局与缓存一致性（一等约束）

```text
[0] 系统提示词                 ← 字节级稳定，永不改写
[1] 案件背景                   ← 字节级稳定，永不改写
[2] 调查进展摘要               ← 可选；压缩后才出现，累积合并
[3..] 工具调用历史（原文）      ← 从保留点开始，最近几轮保持原文
[last] 进度状态                ← 每轮变，只重算这一条
```

三条硬规则：

1. **稳定前缀永不改写**：`[0]`、`[1]` 一旦构造，之后逐字节复用。
2. **动态内容放尾部**：进度 JSON、轮次提醒合并进 `[last]`，每轮只重算这一条。
3. **压缩产物写入时定型**：`[2]` 摘要一旦生成即定型，直到**下一次触发压缩**才被新摘要替换（这是低频事件，缓存断裂是可接受的代价）。

## 5. 触发与压缩

### 5.1 触发条件

```
使用率 = 总消息估算 token / 窗口(100K)
使用率 >= 70% → 触发压缩
```

总消息 = ①②③④ 四块加起来。用轻量估算器（见 §6）计数，不追求精确。

### 5.2 压缩方式（LLM 压缩，非字段抽取）

1. 把**旧的工具历史**（`[3..]` 里要压掉的那部分）连同**已有摘要** `[2]`（若有），交给 LLM 生成**新的调查进展摘要**。
2. 摘要**累积合并**：新摘要必须继承旧摘要已记录的内容，再并入本轮被压掉的工具历史里的新信息，不能从头重写、丢信息。
3. 摘要用**结构化格式**，强制包含这些维度：
   - 已查了哪些数据领域（domain → 关键发现）；
   - 发现的关键证据（谁、对什么、做了什么，含可追溯的 evidence_id / activity_id）；
   - 已确认的实体关系（进程→文件、进程→网络端点等）；
   - 尚未查 / 待确认的缺口。
4. 压缩后，`[3..]` 只保留**最近 N 条工具原文**（默认保留最近 6 条 trace），更旧的全部进摘要。

### 5.3 与进度投影的关系

进度投影（§7）是**每轮由确定性代码从 state 算出的快照**，始终保留、始终在尾部；LLM 摘要（`[2]`）是**历史长到 70% 后的浓缩归档**。两者互补，不冲突：进度投影回答"现在到哪了"，摘要回答"之前一路查到了什么"。

## 6. 轻量 token 估算器

新增 `shared/tokenizer.py`，字符启发式（不引入真实 tokenizer 依赖）：

- CJK 字符每个计 `0.6`；其他字符每个计 `0.25`；结果 `max(1, int(...))`。
- 只用于"是否到 70%"的触发判断，不追求精确。

## 7. 进度投影（结构化 JSON，放尾部）

每轮由确定性代码从 `state.tool_ledger` 算出：

```json
{
  "round": 6,
  "queried_domains": {"process": {"queries": 2, "returned": 5}, "file": {"queries": 1, "returned": 2}},
  "unqueried_domains": ["reputation", "persistence"],
  "explored_entities": {"process:server-01:1234:...": {"resolved": 2, "candidate": 3}},
  "evidence_refs": 18,
  "authorized_scope": {"host_ids": ["server-01"], "allowed_domains": ["process", "..."]}
}
```

- `queried_domains`：7 个域查询工具（封闭集合），映射权限域 → activity_type。
- `explored_entities`：`explore_entity` 已探索过的实体（去重）及各发现的 resolved/candidate 关系数。
- **不注入任何"请结束调查"的硬性提示**，模型从进度数据自行判断。

## 8. 已确认决策

1. **触发**：总消息估算 token ≥ 窗口 70% 时触发压缩。
2. **压缩方式**：LLM 压缩，结构化、累积合并，尽可能保留有价值信息。
3. **进度投影**：结构化 JSON，放尾部。
4. **窗口规格**：模型资源配置项，初始 100K。
5. **前缀一致性**：稳定前缀不变，动态内容放尾部，压缩产物写入时定型。

## 9. 明确不做

| 项 | 不做 | 理由 |
|---|---|---|
| 无条件字段抽取降级（brief_result 进 context） | ❌ | 已否定，会丢有价值信息 |
| chrys 4 阶段压缩 / spill 磁盘归档 / 配额 | ❌ | demo 规模用不上 |
| 真实用量自校准 | ❌（缓做） | 启发式估算对 demo 够用 |
| 按"条数"截断 | ❌ | 语义错位，已被 70% 触发替代 |
