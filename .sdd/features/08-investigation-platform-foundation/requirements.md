# Investigation Platform Foundation Requirements

## 1. 目标

建设面向 AI 调查的数据与治理基础，使未知文件在 CDE 黑白判定后进入后门、勒索和数据泄露调查。系统通过统一数据接口向 LLM 提供规范化活动、字段语义、查询约束和本次执行事实；LLM 负责检查实际数据并判断结论能否成立。

本 Feature 交付四项能力：

1. 安全活动模型与数据接入底座；
2. 正式调查报告契约；
3. 持久化运行、可观测性和审计；
4. 最小调查运行接口。

## 2. 产品边界

- 数据底座是调查产品的一部分，由项目推动客户协助采集，并负责规范化、存储、查询和治理。
- 系统不建设通用 SIEM 或缩小版 Sentinel；Microsoft Sentinel 仅作为数据分层、规范化和存算解耦的架构参考。
- 首期以未知文件调查为产品场景，数据与案件契约不得绑定单一攻击类型。
- 原始记录全部进入本系统存储；采集前脱敏不属于本期范围。
- 首期按百万级规范化活动进行容量设计取舍，不执行百万级数据基准测试，也不承诺数据湖级容量。
- RAG 和生产处置执行不在本期实现。

## 3. 安全活动模型与数据接入底座

### 数据语义

- 数据层不得给活动标注平台最终的攻击或正常结论。
- 上游产品自带的恶意标签只能作为外部检测信号保存，不能直接成为平台 Verdict。
- 客观活动、实体、案件 Evidence、分析结果和案件状态必须分层存储。
- 支持攻击假设和合法解释所需的客观上下文均可进入数据层；系统不另建 CDE 白名单能力。
- 同一活动可以被多个案件引用，不得因 `case_id` 复制为多份底层遥测。

### 原始记录与规范化

- 原始记录必须保留租户、来源、来源记录 ID、事件时间、接收时间、原始载荷引用、内容摘要及 Connector/Parser 版本。
- 数据持久化前完成规范化；首期活动域至少包括进程、网络、Socket、文件、服务、软件包和资产上下文。
- 特殊来源允许使用开放扩展载荷，但外层信封、来源、时间、主体、权限和原始引用不可省略。
- Parser 必须版本化并有样例测试；修复 Parser 后能够重新处理已有原始记录。
- 首期接入协议保持简单，完整采集组件作为后续独立 Feature 建设。

### 实体与关系

- 至少支持 Host、File、Process、User、NetworkEndpoint、Package、Service 和 BusinessAsset。
- 实体解析必须考虑来源标识、时间有效性和标识置信度，不能仅用 PID、IP、路径或主机名认定同一实体。
- 确定性解析负责判断记录是否属于同一实体；LLM 只判断已关联活动对案件假设的相关性。
- 不确定关系必须保持候选状态及歧义原因，不能静默升级为事实。
- 关系必须引用产生它的活动，并能够从活动重新构建；首期不要求专用图数据库。

### 查询与存储解耦

- 研判引擎只能依赖规范化查询契约，不得依赖 SQL、KQL、表名、文件路径或具体存储 SDK。
- 查询按活动域提供强类型条件，共享 Scope、时间、分页和访问上下文。
- 存储适配器负责把规范化查询翻译为实际查询语言；替换存储技术不得修改研判流程。
- 首期存储实现必须具备面向百万级活动的索引、分页和批量写入设计，并为后续关系数据库、湖仓或外部平台适配保留替换边界；实际容量通过后续专项性能需求验证。

### 查询接口与数据约束

- 每个活动查询接口必须向 LLM 公开活动类型、字段语义、可用过滤条件、关联键、排序、分页上限和时间范围限制。
- 每次查询必须返回实际应用的主机、实体、时间、过滤条件、来源、返回数量和下一页游标。
- 数据层只陈述接口定义、查询输入、实际执行边界和返回记录，不评价数据是否完整、是否足够或质量高低。
- “没有数据”“数据不足”“是否发生过”由 LLM 根据接口约束、本次返回和后续查询自行判断。
- 导入报告只记录收到、成功、重复、失败、实际时间范围和实际活动域，不把这些事实换算成 Coverage 等级。

### LLM 调查工具

- LLM 工具按数据能力设计，不按后门、勒索、数据泄露等攻击场景设计。
- LLM 首期只直接使用四个数据工具：`query_activities`、`explore_entity`、`get_raw_records` 和 `calculate_activity_metrics`。
- 在线模型必须通过原生 Tool Calling 接收完整工具 JSON Schema，并以标准 `tool_calls` 发起调用；不得依赖系统提示词手写工具参数协议。
- 每次工具调用结果或错误必须以相同 `tool_call_id` 回灌模型消息历史，并进入运行事件。
- `query_activities` 使用活动类型区分参数结构，由 Tool Gateway 路由到各活动域的强类型查询端口；不得退化为任意字典、SQL 或存储查询语言入口。
- `explore_entity` 统一提供身份、确定关系、候选关系和时间线；返回结果必须保留关系解析状态。
- `get_raw_records` 只能读取本次运行已获得的 Activity 所引用的原始记录，并限制记录数量和返回大小。
- `calculate_activity_metrics` 只执行进程树、连接模式、传输和文件变化等客观计算，不输出攻击类型或威胁结论。
- 租户、案件、运行标识和授权 Scope 由运行上下文注入，LLM 不得自行提交或修改。
- `request_scope_expansion` 和 `finish_investigation` 是流程动作，不计入数据工具；Scope 扩大仍按现有审批中断处理。

## 4. 正式调查报告

- 后端必须发布结构化调查报告，页面不得根据数据集名称或预置场景硬编码攻击影响和反证。
- 报告至少包含威胁结论、攻击现状、影响范围、关键攻击链、支持证据、反证、未解决问题、数据边界和结论限制。
- 最终威胁研判及自然语言说明由 LLM 生成；Fact、Finding 和引用仍受确定性校验。
- 发布校验必须阻止无来源事实、越出实际查询 Scope 的结论和不存在的引用；结论是否获得充分数据支持由 LLM 根据查询约束判断并说明。
- 处置建议必须继续作为独立 `ResponsePlan` 发布，不得混入调查报告。

## 5. 持久化运行、可观测性与审计

- 服务重启后必须能够查询调查运行、节点状态、结果和关键审计记录。
- 运行状态不得只保存在进程内线程字典中。
- 可观测记录至少包含图节点、模型调用、工具查询、校验修复、耗时、Token、重试和错误关联信息。
- 审计记录至少包含运行来源、Scope、模型与 Prompt 版本、调查动作、数据引用、报告版本和现有审批中断结果。
- 可观测日志和不可变审计必须分开管理，均使用统一关联 ID；不得记录 API Key。
- 审计链必须能够按案件运行重建关键处理顺序。

## 6. 最小调查运行接口

- 提供创建调查运行、查询运行状态和读取调查结果的接口。
- 调查标识、当前阶段、运行事件和输出结果必须持久化，服务重启后仍可查询。
- 保留现有 LangGraph Scope 和处置审批中断契约，不建设通用审批服务。
- Demo 可以通过预设策略处理审批中断，并将决定写入审计。
- `ResponsePlan` 必须明确标记审批要求；本期不执行隔离、删除、封禁等生产动作。
- 完整案件生命周期、取消、重试、用户角色、租户授权和人工审批中心后置到独立需求。

## 7. 验收条件

- 同一底层活动可被不同案件引用，底层活动不含 `case_id` 所有权。
- 至少两种来源格式能够通过不同 Parser 产生相同活动域契约，并由相同查询工具消费。
- 文档必须说明百万级活动假设下的索引、分页、批量接入、数据库增长和存储替换策略；本 Feature 不设置实测性能门槛。
- LLM 能同时获得查询接口定义、实际执行边界和返回活动，并据此区分接口限制与实际空结果。
- LLM 通过四个稳定数据工具完成活动查询、实体导航、原始记录回溯和客观计算；新增活动域不要求新增 LLM 工具。
- 调查报告全部来自后端正式契约，展示层删除基于预置数据集语义的结论硬编码。
- 服务重启后调查运行、运行事件、结果和关键审计记录可恢复查询。
- Scope 和处置审批中断继续按既有策略工作，且不会触发生产处置动作。
- 现有双 LLM 循环、数据质量 Demo、RAG Null Adapter 和架构依赖测试不退化。
