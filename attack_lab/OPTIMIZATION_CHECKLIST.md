# 评测效率优化 — 自审清单（每次调整后逐条打勾）

> 目标：质量不下降的前提下缩短单案评测时间。
> 严禁过拟合：调整必须具备通用性（不针对特定案例/特定答案）。

## 瓶颈数据（c2-malicious-elf 典型案，总 1578s / 33.5万 tok）

| 阶段 | 次数 | 耗时 | 占比 | input_tok | 说明 |
|---|---|---|---|---|---|
| judgment_report | 3 | 1071s | 68% | 88,653 | 首次 input 68k + output 19k（含 thinking）；后续两次为修复重试各 10k input + 24k output |
| judgment_planning | 7 | 316s | 20% | 134,242 | 上下文从 4k 增长到 29k，7 轮 |
| response_advisory | 1 | 191s | 12% | 4,714 | 正常 |

**核心瓶颈：报告合成阶段占 68% 耗时 + 68% input token。**

## 优化方向（按优先级）

### A1: 报告合成输出预算优化
- [ ] output_tokens 19k-24k / 次——thinking 模型在报告阶段"过度思考"
- [ ] 探索 `thinking_budget` / `reasoning_effort` 参数（API 是否支持降低思考量）
- [ ] 通用性检查：这是模型参数级别调整，对所有案例统一生效 ✓

### A2: 报告合成 input 瘦身
- [ ] 首次 input 68k token——调查上下文全量灌入报告合成
- [ ] 探索：报告合成是否只需最终判定+证据摘要而非全部中间过程
- [ ] 通用性检查：如果只改报告合成的上下文构建方式（所有案例统一），✓
- [ ] 过拟合风险：如果针对某类案例特殊裁剪 → ✗ 禁止

### A3: 规划轮次收敛
- [ ] 7 轮规划，上下文 4k→29k；第 4-7 轮的 input 跳跃 10k→24k
- [ ] 可能原因：中间某轮触发了上下文压缩（70% 窗口），压缩本身也花时间
- [ ] 探索：max_iterations 是否可从 7 降到 5？需验证不影响判定质量

### A4: 并发度
- [ ] 当前 workers=2；如果网关支持可试 3-4
- [ ] 前提：单案内模型调用是串行的，并发只加速"多案并行"
- [ ] 风险：网关过载反而变慢

## 每次调整后的自审（逐条打勾）

### 通用性
- [ ] 调整对所有案例统一生效（非针对特定 case_id / 特定判定结果的 hack）
- [ ] 不含"如果判定是 X 就 Y"之类的条件分支
- [ ] 改动在管线/框架层，不在数据/GT/评分口径层

### 质量保障
- [ ] 全量测试通过（pytest 全绿）
- [ ] 评测结果的方向正确率不降（对比基线）
- [ ] 判定等级距离不降（对比基线）
- [ ] 没有删除/削弱任何质量校验（边界检查、接地校验、降级纪律）

### 过拟合防范
- [ ] 没有看到答案后调参数（调完再跑同一套题"恰好过了"不算）
- [ ] 如果调整涉及 Prompt/上下文裁剪：裁剪逻辑基于结构而非内容
- [ ] 对比运行用 fresh 参数（全部重采样），不摘 cherry-pick
- [ ] 至少抽 2 个案例人工核对调查报告的逻辑完整性没变

## 实验记录

### 实验1: REPORT_MODEL_MAX_TOKENS 压缩
- 32768→8192: ✗ 截断（ReportDraft JSON 需 15-22k token）
- 32768→12288: ✗ 同上
- 结论: 模型需要完整空间写结构化报告，压缩=截断=失败

### 实验2: RESPONSE_MODEL_MAX_TOKENS 压缩
- 16384→4096: ✗ 截断
- 结论: 同上

### 实验3: tool_choice any→tool(named)
- 速度: 不变（模型输出总量不变，只是从文本 preamble 挪到 JSON 字段）
- 质量: ✗ 下降（13/18 vs 15/18 ok，方向正确率 46% vs 60%）
- 结论: 前导文本不是浪费，是模型的思考空间。强制直接产出工具调用
  导致复杂报告的组织结构能力下降。已回退。

### 总结
- 当前唯一有效优化: workers 2→3（墙钟时间缩 33%）
- 真正瓶颈: 报告合成阶段 55-143k input token（输入与输出成正比）
- 下一步方向: 给报告合成传调查摘要而非全史（架构级改动）
